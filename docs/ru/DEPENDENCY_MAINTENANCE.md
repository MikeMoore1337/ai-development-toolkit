# Сопровождение зависимостей (Issue #64)

[English source](../DEPENDENCY_MAINTENANCE.md)

Опциональный профиль dependency-maintenance помогает обоснованно обновлять библиотеки, **но не обновляет их автоматически**. Новый навык добавлен в существующее расширение Operations и переиспользует minimal-safe-change, code-review, security-engineering, release-safety и узкие QA/SRE-проверки.

## Для новичка

Зависимость - сторонняя библиотека или инструмент приложения. **Прямую** зависимость указал разработчик; **транзитивная** нужна другой библиотеке. Манифест содержит заявленные версии, а **lockfile** фиксирует разрешённые версии зависимостей и их состав. Когда полный граф неизвестен, результат - TRANSITIVE_DEPENDENCIES = UNKNOWN.

Запрос: «Проверь, какие зависимости действительно нужно обновить, какие риски есть, как проверить совместимость и всё восстановить. Не меняй ничего без разрешения».

SemVer - соглашение о версиях major/minor/patch, а не доказательство совместимости. Даже PATCH может ломать приложение. **Breaking change** - изменение API, поведения, конфигурации, runtime, формата данных или протокола, нарушающее работу старого клиента, даже если библиотека успешно установилась. Новейшая версия не обязательно лучше подходящей стабильной.

## Порядок и доказательства

Инвентаризация → конкретная причина (security, compatibility, bug-fix, feature, maintenance, optional) → проверенные release notes и advisories → сравнение manifest и lockfile → транзитивное воздействие → анализ breaking changes/лицензий/источников → матрица совместимости → проверки по риску (статические, модульные, контрактные, интеграционные, сквозные, запуск в целевой среде) → ограниченное изменение с разрешением → план отката и фактическое подтверждение.

| Область | Подтверждение |
| --- | --- |
| Security advisory | Точный пакет, экосистема, установленная версия, affected/fixed range, официальный источник и условия эксплуатации |
| Изменения | Changelog, migration guide, изменения API, настроек и лицензии |
| Lockfile | Все прямые и транзитивные изменения, источник, контрольная сумма, платформа, лицензия |
| Совместимость | Раздельно SUPPORTED_BY_SOURCE и фактически TESTED_PASS |
| Восстановление | Старый SHA, manifest, lockfile, окружение и проверка работы/данных |

Источники: уведомления авторов, GitHub Security Advisories, OSV, NVD, базы менеджеров пакетов. Отсутствие известных CVE в проверенных источниках не гарантирует безопасность. Если проверка сети недоступна, не заявляй подтверждённый актуальный статус.

Git revert восстанавливает код в репозитории, но не фактически установленную зависимость и не данные production. Для необратимых изменений данных статус ROLLBACK_BLOCKED и план исправления вперёд. Зелёный CI подтверждает только пройденные тесты в соответствующих средах.

## Примеры и ограничения

Включены **два синтетических** примера: обычное обновление с транзитивным изменением и поломкой старого API; условное security-обновление с диапазоном затронутых версий, runtime и связанными пакетами. Есть 20 отрицательных сценариев. Это не действующие CVE и не результат настоящего сканера.

Для проверки фикстур самого Toolkit, без сети и установки пакетов:

    python scripts/validate_dependency_maintenance.py
    python -m unittest discover -s tests -p 'test_dependency_maintenance.py' -v

Python standard library нужна только этим **внутренним тестам**, а не пользователям навыка. Не подключаются платные сервисы, внешние API-ключи, Dependabot, Renovate и фоновые обновления. В других проектах Toolkit остаётся read-only; отчёты по умолчанию выдаются в чате. Фактическая совместимость пакетов, проверка реальных advisories, production rollback и активация навыка в ИИ-клиенте - NOT_MEASURED.
