# DevOps и инфраструктура (Issue #61)

[English version](../DEVOPS_INFRASTRUCTURE.md)

Необязательный навык `devops-infrastructure` помогает определить инфраструктуру, проверить CI/CD, конфигурации контейнеров и Infrastructure as Code (IaC), подготовить публикацию и восстановление. Он не создаёт второй контроллер выпуска и не запускает настоящие инфраструктурные операции. Docker, Kubernetes, Terraform, платные API и облачные сервисы не обязательны.

## Начинающий пользователь

> Помоги настроить автоматические проверки и безопасную публикацию приложения. Сначала изучи мой проект, используй бесплатные инструменты. Не добавляй Docker без необходимости и ничего не запускай на сервере без отдельного разрешения.

**CI** - автоматическая проверка кода конкретной ревизии. **CD** - процесс доставки и, при необходимости, развёртывания. Сборка создаёт артефакт, но не означает, что приложение работает на сервере. Контейнер упаковывает приложение и окружение; многим локальным приложениям он не нужен.

## Последовательность

1. Изучить реальные языки, сборку, тесты, CI, среды, хранилища, миграции, права и восстановление. Неизвестное помечать `UNKNOWN`, предполагаемое - `ASSUMED`, подтверждённое - `CONFIRMED`, неприменимое - `NOT_APPLICABLE`.
2. Переиспользовать `security-engineering`, `database-migrations`, `reliability-testing`, `failure-triage` и `release-safety`, а не создавать их копии.
3. Составить CI/CD-контракт: SHA исходника, триггер и доверие, зависимости, этапы с условиями успеха/ошибки, обязательные проверки, права, ссылки на секреты без значений, checksum и происхождение артефакта, среда, разрешение и доказательства.
4. Проверять контейнеры, только если они используются или явно запрошены: образ, контекст сборки и секреты, пользователь, запуск, здоровье и ограничения. Статическая проверка Dockerfile не подтверждает собранный или запущенный контейнер.
5. Для IaC отделять текущее и желаемое состояние, изменение/удаление/расходы, синтаксическую проверку, настоящий plan, отдельное разрешение, фактический apply и проверку результата. Синтетический plan не подтверждает состояние облака.
6. Разделить local, CI, test, staging, production по владельцу, доверию, данным, секретам, стоимости и правам. Имя staging не гарантирует изоляцию от production.
7. Составить план развёртывания: точный артефакт и владелец, порядок expand/migrate/contract, предпроверки, способ выкладки, условия остановки, smoke/health, мониторинг, откат и forward-fix. Готовность передавать в существующий `release-safety`.
8. Не переходить от `PLAN_VALIDATED` к `APPLY_AUTHORIZED` без конкретного разрешения. Зелёный CI, dry-run и слитый PR не доказывают `APPLIED` или `POST_APPLY_VERIFIED`.

**Восстановление:** откат кода не отменяет необратимую миграцию данных. Наличие резервной копии не доказывает возможность её восстановить. Уровни доказательств `SOURCE_REVIEWED`, `CONFIG_VALIDATED`, `PLAN_VALIDATED`, `APPROVAL_VERIFIED`, `APPLY_EXECUTED`, `DEPLOYMENT_VERIFIED`, `RECOVERY_TESTED`, `NOT_TESTED`, `BLOCKED` нельзя подменять друг другом.

## Автономный пример без платных инструментов

```bash
python scripts/validate_devops.py
python -m unittest tests.test_devops -v
```

В `fixtures/devops/cases.json` находятся вымышленный корректный конвейер и 18 неисправных вариантов. Скрипт не использует внешнюю сеть, реальные Docker/IaC, VPS, облако, БД или восстановление. Проверка активации навыка реальными ИИ-клиентами - `NOT_MEASURED`. При использовании Toolkit в чужом проекте копия Toolkit остаётся только для чтения; отчёт возвращается в чат, если другое место не согласовано.
