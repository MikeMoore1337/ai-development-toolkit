# Воспроизводимая процедура выпуска релиза

[English source](../RELEASE_PROCESS.md) | [Правила публикации](PUBLICATION_POLICY.md) | [Языковая политика](LANGUAGE_POLICY.md)

В репозитории используется поставка через Pull Request. Успешный CI на PR необходим, но **не заменяет** отдельную проверку фактически опубликованного тега и архива.

## Опубликованный v5.5.0: несоответствие метаданных (21.10.2026)

Последний опубликованный выпуск GitHub - [v5.5.0](https://github.com/MikeMoore1337/ai-development-toolkit/releases/tag/v5.5.0), SHA тега `04d60055e93c04dda26fb3868689ab4031fbf617`. **В содержимом опубликованного тега `MANIFEST.json.version = 5.4.0`, а журнал изменений и инструкции называют последним выпуском v5.4.0.** Это несоответствие метаданных; существующий опубликованный тег нельзя незаметно передвигать или переписывать. Публичный выпуск идентифицируется тегом, но устаревшую версию внутри архива необходимо честно указывать. Исправления только вперёд, см. [Issue #153](https://github.com/MikeMoore1337/ai-development-toolkit/issues/153). Остальные инструкции ниже подготовлены для предполагаемого выпуска v5.5.1. До фактической публикации тега и GitHub Release последним опубликованным релизом остаётся v5.5.0; не утверждайте, что кандидат уже выпущен. Перед следующим релизом требуется заново проверить права, совпадение манифеста и тега, состав архива и фактические доказательства.


## Версии и состояние выпуска

- `MANIFEST.json.version` обозначает **последний опубликованный базовый релиз** (для исправленного выпуска `5.5.1`), а не версию каждого последующего коммита `main`.
- `CHANGELOG.md` содержит раздел `Unreleased` для изменений после последнего тега. Последний опубликованный раздел должен иметь пометку `released`, а не `prepared`. Исторические записи сохраняются.
- Идентичность опубликованного релиза определяется неизменяемым Git-тегом и GitHub Release **на точном SHA**. `main` — ветка разработки, которая может опережать опубликованный тег. Не называйте установку `main` опубликованным архивом.
- Лишь после release preflight и **явного решения владельца** можно выбрать следующую версию, обновить манифест и подготовить отдельный релизный PR/тег. CI никогда не выпускает новую версию автоматически.
- Проверки исходников не равны runtime-доказательствам: правильный формат или успешное копирование не доказывают обнаружение навыков клиентом, их активацию или пользу.

Текущая база: [v5.5.1](https://github.com/MikeMoore1337/ai-development-toolkit/releases/tag/v5.5.1), выпуск 21 октября 2026 года. Точный SHA проверяется по опубликованному тегу. [Сравнение v5.5.1...main](https://github.com/MikeMoore1337/ai-development-toolkit/compare/v5.5.1...main) показывает последующие изменения. Исторический [v5.5.0](https://github.com/MikeMoore1337/ai-development-toolkit/releases/tag/v5.5.0) оставлен без изменений, включая неверный номер 5.4.0 в его метаданных.

## Порядок выпуска

1. Работайте в отдельной ветке; опишите изменения и риски миграции.
2. Установите зависимости: `python -m pip install -r requirements-dev.txt`.
3. Выполните `python scripts/check_public_package.py`, `python scripts/validate_pack.py` и `python scripts/validate_provenance.py --mode inventory`.
4. Запустите `python -m unittest discover -s tests -v`.
5. После проверки diff обновите хеши командой `python scripts/verify_checksums.py --write`, **ещё раз изучите получившийся diff**. Реестр охватывает отслеживаемые файлы на момент формирования, кроме себя. Нельзя пересоздавать хеши лишь для сокрытия неожиданных изменений.
6. Выполните `python scripts/verify_checksums.py` и сравните байты с реестром.
7. Если официальный demo CLI установлен из доверенного закреплённого источника, можно выполнить `python scripts/validate_with_skills_ref.py --scope all`. Установка и запуск отделены от CI, автоматической сетевой установки здесь нет.
8. Проверьте, что diff не содержит ключи, токены, приватные данные, нелицензированные материалы или неожиданные исполняемые файлы. Встроенный сканер — **базовая защита**, не полноценный анализ секретов и supply chain.
9. Откройте PR, дождитесь **всех** заданий CI (Ubuntu Python 3.12/3.13, Windows 3.14), разберите комментарии и только затем выполняйте разрешённое слияние. Правила владельца и ограничения деплоя обходить нельзя. Реальная конфигурация GitHub Ruleset находится в GitHub, а не в исходниках.
10. **Перед созданием любого тега или GitHub Release** выполните `python scripts/validate_provenance.py --mode release` на дереве предполагаемого релиза. Если результат `BLOCKED` — **не публикуйте**: разберите каждый ограниченный компонент, проверьте документы о правах вне репозитория и сохраните несекретную запись либо отдельно согласуйте обратимое исключение. Этот ручной шаг **обязателен даже после успешного CI**, проверившего inventory и release-preflight. Дополнительно CI проверяет чистый офлайновый `git archive` на Ubuntu 3.12, но GitHub-архивы **новых** тегов требуют отдельной проверки. Сообщённое разрешение владельца `ID1337` относится к SHA256 и классификациям **44 исходных компонентов (75 файлов)**; изменённые, добавленные или переклассифицированные материалы в этой области требуют нового рассмотрения. Успех snapshot gate подтверждает только совпадение файлов с зафиксированным решением, **не** независимое разрешение правообладателя или работодателя.
11. Только после успешного CI на `main` **и** отдельного release rights gate создайте тег на точном проверенном SHA, опубликуйте примечания о совместимости и проверьте фактический архив. Не объявляйте релиз проверенным на реальных агентах без соответствующих испытаний.

Текущие настройки Ruleset: [защита ветки (EN)](../BRANCH_PROTECTION.md). CI проверяет структуру навыков, но переносимость и эффективность реальных агентов требуют отдельных испытаний.

## Независимая проверка GitHub-архива исходников

До публикации нового релиза скачайте **фактический** ZIP, созданный GitHub, и распакуйте в **новую пустую папку**, не в Git clone или уже использовавшийся worktree. Пример для Windows (замените тег проверяемого релиза):

```powershell
$tag = "v5.5.1"
$zip = Join-Path $env:TEMP "adt-$tag.zip"
$dest = Join-Path $env:TEMP "adt-$tag-source"
if (Test-Path $dest) { throw "Destination must be fresh: $dest" }
Invoke-WebRequest "https://github.com/MikeMoore1337/ai-development-toolkit/archive/refs/tags/$tag.zip" -OutFile $zip
Expand-Archive -LiteralPath $zip -DestinationPath $dest
$root = Get-ChildItem $dest -Directory | Select-Object -First 1
python scripts/verify_checksums.py --archive-root $root.FullName
$manifest = Get-Content (Join-Path $root.FullName "MANIFEST.json") -Raw | ConvertFrom-Json
if ("v$($manifest.version)" -cne $tag) { throw "TAG_MANIFEST_VERSION_MISMATCH" }
```

Проверка архива сравнивает SHA256 и требует, чтобы **каждый извлечённый исходный файл встретился ровно один раз** в `SHA256SUMS.txt`. Отклоняются недостающие, лишние, неучтённые файлы и пути через ссылки. В Git worktree режим `git ls-files -z` даёт канонический список отслеживаемых файлов, поэтому новые отслеживаемые файлы тоже требуют контрольных сумм.

Проверка сама по себе **не удостоверяет загруженный архив и издателя**: отдельно проверяйте ожидаемый SHA тега и результат workflow GitHub. Для публикации нужен **реально выполненный и зафиксированный** архивный тест; описание инструкции не доказывает, что архив когда-либо был скачан.

После публикации GitHub Actions `Verify release source archive` запускается при отправке релизного тега и событии `release: published`. Его также можно вызвать вручную для допустимого тега `vX.Y.Z`. Перед подтверждением приёмки архива проверьте фактически завершённый job и артефакт `release-source-verification`. В отличие от статической проверки дерева Git, этот workflow сверяет **реально загруженные байты** и отклоняет архив, если версия в `MANIFEST.json` отличается от номера тега. Проверка после создания тега не может отменить публикацию: номер версии следует сверять до неё.

Новые архивы проходят release provenance gate после проверки SHA. Исторические архивы без соответствующего скрипта получают `NOT_VERIFIED` по лицензиям, сохраняя независимый результат проверки хешей: права на их повторное распространение **не считаются подтверждёнными задним числом**.
