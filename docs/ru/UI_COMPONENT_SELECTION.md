# Выбор UI-компонентов: shadcn/ui и Magic UI (переносимый протокол, #408)

Это **локальный протокол выбора**, не установщик, React-фронтенд, разрешение на дизайн или новый контроллер UI. Используется существующими навыками `component-architecture`, `motion-quality`, `ux-ui-design-orchestra` для любого целевого проекта; его `AGENTS.md` и принятая дизайн-система важнее внешних примеров.

## Источники и ограничения

- [shadcn-ui/ui](https://github.com/shadcn-ui/ui): архитектура React-примитивов и реестров; многие варианты требуют Tailwind, Radix/Base UI. Проверять **лицензию каждого переносимого файла**, нужные атрибуции и зависимости.
- [magicuidesign/magicui](https://github.com/magicuidesign/magicui): эффекты и композиции на React; отдельные варианты требуют Motion и Tailwind. Оценивать расходы производительности, доступность и `reduced-motion`.
- Toolkit не включает исходники, установщики, CSS и runtime внешних пакетов. Одна ссылка = `REFERENCE_ONLY`, а не работающая интеграция. Платные API и модели не требуются.

## Порядок

1. Указать наблюдаемую проблему, SHA, маршрут, состояние, размер экрана и фактический screenshot. Непроверенное = `HYPOTHESIS`.
2. Сначала проверить уже имеющиеся кнопки, формы, меню, focus/selected состояния, токены, темы, CSS и Web Animations API. `REUSE_EXISTING` предпочтительнее ненужной новой библиотеки.
3. При дефиците выбрать **конкретный компонент**, не весь фреймворк. Зафиксировать URL оригинала, точный commit, реальную лицензию/уведомления; при неясной лицензии/ревизии не копировать.
4. Сверить новые Tailwind, Radix, Base UI, Motion и другие зависимости с реализацией средствами стандартного CSS/React. Новые пакеты допустимы только при конкретной пользе.
5. Перед заметным изменением интерфейса предоставить реальные Dark/Light макеты desktop/mobile, при необходимости кадры `reduced-motion`. Макет = `PROPOSAL_ONLY`, не `OWNER_ACCEPTED`.
6. После **предметного визуального согласования** внедрить только согласованную версию в целевой репозиторий с клавиатурой, ARIA/названиями, focus, contrast, мобильными касаниями и альтернативой без анимаций. При новых зависимостях измерить размер сборки до/после.
7. Выполнить тесты текущего SHA, PR CI и требуемый smoke после релиза. Синтетический тест или ссылка на upstream не подтверждают работу интерфейса.

## Добровольная структурная проверка

```sh
python scripts/validate_ui_component_adoption.py /path/to/local-ui-candidate.json
```

CLI ничего не скачивает, не устанавливает, не пишет и не запускает браузер. Пакет JSON должен иметь ровно поля `schema_version`, `candidate`, `source`, `decision`, `consumer_revision`, `observed_problem`, `reuse_evidence`, `license`, `source_revision`, `new_dependencies`, `performance`, `accessibility`, `reduced_motion`, `visual_evidence`, `owner_approval`, `tests`, `remote_services`. Значение `REUSE_EXISTING` или `PROPOSAL_ONLY` не выдаёт разрешение на код. Для внешнего компонента нужны подтверждённые сведения о лицензии и полный upstream SHA.

`IMPLEMENT_APPROVED` допускается только при реальном SHA потребительского проекта, свидетельстве `OWNER_ACCEPTED`, ссылках на настоящие скриншоты, испытаниях доступности и `reduced-motion`, `PASS_EXACT_SHA` и измеренных байтах до/после при добавлении runtime зависимостей. Даже такой структурный PASS **не означает**, что агент действительно проверил браузер, тесты или разрешения: доказательства должны быть получены в целевом проекте. Не сохранять в Toolkit его скриншоты, секреты, пути, отчёты и пользовательские данные.

Честный завершённый вывод может быть `REUSE_EXISTING` с подтверждением достаточности текущего решения; при необходимости новой композиции сначала готовить проверяемые макеты, затем запрашивать отдельную визуальную приёмку.
