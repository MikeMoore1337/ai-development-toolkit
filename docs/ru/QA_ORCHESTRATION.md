# QA Orchestra - независимая проверка без второго контроллера

[English](../QA_ORCHESTRATION.md)

Это **необязательный процесс QA внутри одной задачи**, а не сервер агентов, планировщик, отдельная система GitHub Issue/PR или новый CI-гейт. Используются существующие `qa-strategy`, `qa-verifier` и профильные навыки QA. Правила AGENTS.md целевого проекта, Issue, границы разрешений, визуальное согласование и политика выпуска имеют приоритет.

## Когда применять

- **Один агент:** опечатка, небольшое изолированное исправление, известная регрессия с простым оракулом. Не вызывать экспертную группу.
- **Два направления:** изменение на границе сервисов, где нужны независимые проверки, например API/авторизация и поведение UI.
- **До трёх направлений:** рискованные сквозные изменения, миграции, несовместимые сигналы, доказательства для критического выпуска. Три - максимум, а не обязательное число.
- У разработки только один управляющий процесс: `feature-delivery` либо явно доступный `make-feature`. QA Orchestra не управляет жизненным циклом Issue, PR или релиза.

## Адаптивный выбор без запуска агентов (Issue #279)

Необязательная команда `scripts/orchestration_decision.py INPUT.json` только **выдаёт детерминированный совет** и ничего не выполняет. Укажите `schema_version=1`, `scope=SMALL|MEDIUM|LARGE`, `independent_readonly_streams=0..3`, `writes_required` (bool), `parallel_capability=VERIFIED|NOT_VERIFIED|UNAVAILABLE`, `owner_parallel_approval`, `zero_incremental_cost_verified`, `isolation_verified`.

- Для маленькой задачи всегда `SINGLE_AGENT`. Для средней/большой обычно `SEQUENTIAL_REVIEW`: один контроллер, последовательные проверки. `OPTIONAL_PARALLEL_READONLY_REVIEW` допустим только при **всех** подтверждениях: минимум два независимых направления на чтение, реально доступный механизм параллельной работы, согласие владельца, нулевые дополнительные затраты, изоляция и **отсутствие записи**.
- Даже при всех подтверждениях это лишь предложение: инструмент создаёт **0 процессов агентов**. Настоящие вызовы и разрешения проверяет клиент; параллельные записи не разрешены.
- Результат содержит коды причин/ограничений. `execution=NOT_RUN`, `client_activation=NOT_VERIFIED`, экономия времени/токенов и польза — `NOT_MEASURED`. Входные заявления не аутентифицируются. Для последующего отчёта о QA используйте прежний `validate_qa_orchestration.py`, не переписывая результаты исторического A/B.
- В трёх исходных A/B случаях один вариант был приблизительно на 49% быстрее, два остальных — на 6% и 4% медленнее. Это неоднородные задачи, а не доказательство общей выгоды или критерии автоматического выбора.

Минимальный синтетический вход:

```json
{"schema_version":1,"scope":"SMALL","independent_readonly_streams":0,
 "writes_required":false,"parallel_capability":"NOT_VERIFIED",
 "owner_parallel_approval":false,"zero_incremental_cost_verified":false,
 "isolation_verified":false}
```

## Процесс

1. **Подготовка:** уточнить критерии задачи, точную ревизию, изменённые компоненты, риск, реально доступные инструменты и границы данных. Сформировать минимальные проверяемые оракулы.
2. **Подбор специализаций:** API/контракты/авторизация (`api-testing`, `contract-testing`); браузер/доступность (`playwright-testing`, `e2e-testing`); Python/БД (`pytest-test-design`, `database-validation`); CI/нестабильность (`failure-triage`, `flaky-analysis`); безопасность (`security-testing`, `security-review`). Не загружать весь QA Pack и не создавать агента на каждый навык.
3. **Независимые задания только на чтение:** передать каждому специалисту критерии, SHA, чёткие границы, ожидаемые тесты и запрет неразрешённых изменений. Принятые дефекты позднее исправляет один ответственный исполнитель в своей ветке.
4. **Реальная параллельность:** при наличии работающего инструмента субагентов запустить максимум три независимые проверки и указать идентификаторы фактических вызовов. Универсальный субагент с инструкцией роли не становится отдельным именованным экспертом. Без субагентов последовательно выполнить проверки и честно указать `SEQUENTIAL`. Никаких новых платных провайдеров.
5. **Объединение результатов:** удалить повторы, воспроизвести существенные сбои, устранить противоречия и связать каждый критерий с оракулом и доказательством. `NOT_RUN` и `UNKNOWN` не являются успешными тестами.
6. **Единый отчёт:** ревизия, фактические исполнители, критерии и риски, статусы тестов/окружения, доказательства, разногласия, пробелы и решение `READY_FOR_REVIEW`, `BLOCKED` или `INSUFFICIENT_EVIDENCE`. `READY_FOR_REVIEW` - лишь готовность к проверке, не разрешение на merge/deploy.
7. **Передача в разработку:** исправления только в разрешённом отдельном шаге с повтором затронутых проверок и актуального CI для текущего HEAD.

## Доказательства и достоверность

Каждое направление фиксирует `id`, область, реально прочитанные навыки, режим `SEQUENTIAL`/`ACTUAL_SUBAGENT`/`GENERIC_SUBAGENT`, след запуска (только если был), оракулы, окружение, SHA, ограничения и ссылки на реальные результаты.

Использовать `PASS`, `FAIL`, `NOT_RUN`, `BLOCKED`, `UNKNOWN`. Для `PASS` и `FAIL` нужны фактически исполненные тесты/CI/браузерные проверки на точной ревизии: просмотр исходников и синтетические примеры не подходят. Переименование собственной проверки в «независимую» не создаёт независимого рецензента. Скриншоты интерфейсов должны существовать и не раскрывать персональные данные.

Дополнительная проверка `scripts/validate_qa_orchestration.py fixtures/qa_orchestra_valid.json` валидирует только **внутреннюю согласованность деклараций**, а не реальность вызовов и файлов. Пример синтетический, тесты `NOT_RUN`. Обычному пользователю JSON-файл не нужен. Валидатор выявляет ложные зелёные статусы и невозможную параллельность, но не аутентифицирует источники.

## Применение к разным типам проектов

- **Веб- или мобильное приложение:** проверяй пользовательские сценарии, доступность, контракты интерфейса/API/БД и существующие правила релиза и визуального согласования.
- **Агентный сервис:** проверяй доказательства инцидента, неопределённость и ограничения модельных вызовов, не расширяя права постоянно работающих процессов.
- **Приложение с приватными данными или внешними действиями:** проверяй границы доступа, согласие, идемпотентность и сверку неопределённого результата только на синтетических данных.

Без новых зависимостей, платных API, фонового выполнения или обязательных файлов отчётов.
