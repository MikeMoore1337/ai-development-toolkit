# UX/UI Design - от требований до передачи в разработку

[English source](../UX_UI_DESIGN.md)

**UX** - что человек хочет сделать и насколько понятен путь к цели. **UI** - как выглядит экран и его состояния. **Wireframe (каркас)** - структурная схема, а не согласованный визуальный дизайн. Статическая картинка ещё не является работающим интерфейсом. **Интерактивный прототип** требует настоящих переходов и фактической проверки действий.

## Начните обычными словами

> Хочу приложение для домашних расходов. Нужно добавлять расходы, видеть итоги, редактировать и удалять записи. Сначала опиши экраны, навигацию и ошибки. Код пока не пиши.

Достаточно обычного описания задачи. **Если нужны только текстовые сценарии и структура экранов**, подходит необязательный профиль `ux-design`. **Для нового сайта, лендинга, макета или существенного редизайна** начинайте с `ui-orchestra` / `ux-ui-design-orchestra`: выполняйте оригинальные методы доступных инструментов, создавайте нужные визуальные варианты и согласуйте конкретную версию перед внедрением. Ссылка на Toolkit в чате помогает получить инструкции, но не даёт доступа к проекту. Figma, терминал, платный API и выбранный фронтенд-фреймворк для обсуждения идеи не обязательны.

## Этапы проектирования

1. **Источник:** системная спецификация, PRD, идея или реально изученный интерфейс. Сохранять исходные R-ID/AC-ID/SR-ID/UC-ID/BR-ID и происхождение фактов. Не выдумывать исследование и неизвестные бизнес-правила.
2. **Исследование:** задача пользователя, роль, контекст, точка входа, трудности, альтернативы и результат. Гипотеза содержит условия проверки и опровержения. Нет наблюдений - NOT_TESTED.
3. **Сценарии:** действия человека, варианты, ошибки, восстановление и достижимое завершение. Достаточно Markdown; Mermaid необязателен.
4. **Информационная архитектура:** минимальный перечень экранов и навигация, через которую каждая роль может выполнить нужное действие.
5. **Каркасы:** зоны и порядок информации, формы, кнопки, переходы, пустые/загрузочные/ошибочные состояния. Текстовый вариант - TEXT_SPEC, а не готовое изображение.
6. **Прототип:** событие, исходное, конечное и ошибочное состояние, переход, доступность и критерий приёмки. INTERACTIVE_VERIFIED - только после реального испытания.
7. **Внешний вид и дизайн-система:** существующий бренд, цвета, шрифты, токены и иконки важнее общего шаблона. Использовать `design-system-consistency` и `motion-quality` для их задач; не создавать второй источник токенов.
8. **Компоненты:** входные данные, выходные события, варианты, валидация, состояния загрузки/блокировки/ошибок, адаптивность и доступность. `component-architecture` помогает передаче в разработку, не навязывая React/Vue/Svelte.
9. **Передача и QA:** источник требований, сценарии, экраны, реально созданные ресурсы, решения, контракты компонентов, доступность/адаптивность, прослеживаемость и открытые вопросы. Реальные реализации проверяются через `screenshot-fidelity` и UI-тесты; совпадение картинки не доказывает работу кнопок.

Пример связи: `R1 -> UC1 -> FLOW-1 -> SCREEN-2 -> COMP-FORM -> AC1/AC2`. [Учёт расходов](../../extensions/design/skills/ux-design-process/references/EXAMPLE_EXPENSES.json) и [многоролeвая панель](../../extensions/design/skills/ux-design-process/references/EXAMPLE_WORKFLOWS.json) - синтетические дизайн-спецификации, а не разработанные приложения.

## Дополнительная проверка качества из трёх открытых проектов

Toolkit использует **методики, а не устанавливает чужие инструменты**: сначала выяснить задачу человека, затем спроектировать интерфейс; проверить реальные границы данных и ошибки; при значимых развилках сравнить различающиеся варианты навигации, структуры или взаимодействий. Субъективную оценку внешнего вида не смешивать с измеримыми техническими проверками. Существующая дизайн-система остаётся основной.

[Дополнительная проверка и стресс-сценарии](../../extensions/design/skills/ux-design-process/references/REVIEW_AND_STRESS.md) содержат примеры длинных переводов, отсутствующих данных, больших чисел, запрета доступа, обрыва сети, повторных нажатий, экранной клавиатуры и safe-area. В [разборе источников](../../extensions/design/skills/ux-design-process/references/INSPIRATION_REVIEW.md) указаны проверенные версии, лицензии, выбранные идеи и причины отказа от копирования пакетов. Сторонние программы, базы дизайнерских шаблонов и бинарные файлы не добавляются.

## Адаптивность и доступность

Для каждого важного экрана задать проверяемые ширины мобильного и настольного интерфейса (планшет при необходимости), фокус, клавиатуру, увеличение масштаба, длинные переводы, экранную клавиатуру, safe-area, переполнение и ошибки. План адаптивности ещё не подтверждает её работу. Учитывать применимые критерии [WCAG 2.2](https://www.w3.org/TR/WCAG22/) и исключения: подписи, фокус, клавиатура, ошибки, контраст, размер активных областей, уменьшение движения. Автоматические, ручные и проверки вспомогательными технологиями учитывать раздельно.

| Артефакт | Корректный статус |
| --- | --- |
| Текстовый экран/сценарий | TEXT_SPEC / PREPARED |
| Реальное статическое изображение | STATIC_RENDER / RENDERED с доказательствами |
| Работающий прототип | INTERACTIVE_VERIFIED после настоящих проверок |
| Реализация кода | IMPLEMENTED, а работоспособность ещё проверяется отдельно |
| Принятый владельцем дизайн | OWNER_ACCEPTED только после явного решения |

Для специалистов: [контракт UX/UI](../../extensions/design/skills/ux-design-process/references/UX_UI_CONTRACT.json), [ручная приёмка](../../extensions/design/skills/ux-design-process/references/MANUAL_ACCEPTANCE.md), [структурный валидатор](../../scripts/validate_ux_ui_spec.py). Успех структурной проверки не означает визуальную приёмку или соответствие WCAG.

## Необязательная установка для текстового проектирования

Команды ниже - **только для профиля `ux-design`** при планировании сценариев без визуальных макетов. Используйте Python 3.12+ из корня Toolkit, а `/path/to/project` замените на папку существующего проекта.

```bash
python scripts/skill_manager.py catalog --profile ux-design
python scripts/skill_manager.py install --target /path/to/project --profile ux-design
```

Сначала проверьте список файлов, затем при согласии отдельно выполните установку и проверку примера:

```bash
python scripts/skill_manager.py install --target /path/to/project --profile ux-design --apply
python scripts/validate_ux_ui_spec.py extensions/design/skills/ux-design-process/references/EXAMPLE_EXPENSES.json
```

Для визуального проектирования сначала выберите `ui-orchestra` и следуйте [процессу создания дизайна](../../.agents/skills/ux-ui-design-orchestra/references/CREATE_DESIGN.md). Копирование файлов само по себе не подтверждает активацию навыка.

Без `--apply` файлы не меняются. Копии Toolkit в чужих проектах **только для чтения**: отчёты и макеты возвращаются в чат, если пользователь не указал разрешённое место сохранения. Реальная активация навыка в ИИ-клиентах, визуальная и пользовательская проверка остаются NOT_MEASURED / NOT_TESTED.


## UX/UI Design Orchestra - нативные методы и сохранение лучших вариантов

**Свобода UI/UX:** оркестратор не запрещает стили, паттерны или визуальные материалы. Следуй **оригинальным методикам инструментов**, реальной задаче, вкусу пользователя и утверждённой дизайн-системе проекта. Hero, карточки, сетки, SaaS-элементы, градиенты, стекло, любые уместные цвета и шрифты допустимы. Нет обязательного количества концепций, эскизов, рисков шаблонности или сравнений с посторонней отраслью.

Создавай именно столько вариантов, сколько оправдано запросом и процессом оригинального инструмента. Если показываешь альтернативы, сначала реально нарисуй и просмотри их, а затем сравни. Не называй ссылку на GitHub выполненным навыком, а текстовое описание - отрисованной картинкой. Для мобильного интерфейса не навязывай настольную версию; для адаптивного магазина полезно проверить обе.

Если владелец предпочёл/принял предыдущий макет, сохрани его версию, ссылки на изображения и сильные стороны **в целевом проекте или чате, не в Toolkit**. Сравни предложенную замену с ним на сопоставимых размерах и состояниях: композиция, типографика, фотография, выразительность и удобство. Если новый вариант не убедительнее, лучше сохранить/доработать прежний. Успешные тесты браузера и CI не измеряют художественное качество.

Реализация интерфейса - только после явного принятия конкретной версии. Реальная активация оригинальных навыков и согласование владельца остаются отдельными проверками. Режим `ALL_THREE` и соответствующие подтверждения описаны в #449.

## Три оригинальных дизайн-навыка без изменений - добровольный режим ALL_THREE (#449)

Постоянный выбор пользователя или прочитанная настройка приватного плагина уже являются включением режима: в обычном запросе не нужно повторять названия навыков. Адаптер ChatGPT читает `skills/toolkit-task-router/references/USER_PREFERENCES.json` в существующем формате настроек. Публичный файл пуст; в личном пакете владелец может сохранить `skills.design_originals=ALL_THREE`. Отсутствие локального файла не сбрасывает известный личный выбор. Явные настройки проекта/задачи и выбранный оригинальный контроллер сохраняют приоритет; новых прав на выполнение эта настройка не даёт.

До отрисовки нужно прочитать каждый выбранный оригинал и проверить его собственную область применения. Явное исключение отмечается `NOT_APPLICABLE_NATIVE_SCOPE` с загруженным источником, ревизией, причиной и ссылкой. Оно не удовлетворяет условию трёх реальных вызовов. Для статического макета выполняются применимые исследование и проектирование; запуск движка, полный процесс и проверка браузером подтверждаются отдельно.

Существующий `ui-orchestra` может совместно применять **три оригинальных сторонних навыка** при выборе `original_design_skills.mode=ALL_THREE`. Toolkit не включает эти внешние оригиналы. Клиент проверяет навыки проекта, родительских папок и пользователя, устанавливает недостающие обязательные оригиналы и инструменты после проверки источника, лицензии, закреплённой ревизии и файлов в пределах выданных прав, затем проверяет установку и вызывает их. Предпочтительна пользовательская область; существующие файлы сохраняются. Явный отказ от установки имеет приоритет; при блокировке нужно указать причину, а не подменять оригинал справочной методикой. Ссылки, файлы и структурная проверка не доказывают вызов. См. [настройку для задачи](INSTALLATION.md#автоматическая-установка-необходимого-для-задачи).

Официальные варианты установки в проект Codex, **только после самостоятельной проверки исходников, лицензий, возможных загрузок и hooks**:

- [Impeccable](https://github.com/pbakaus/impeccable) - Apache-2.0 (сохранить LICENSE/NOTICE): `npx impeccable install --providers=codex --scope=project`. При первом использовании возможна загрузка движка, hooks требуют отдельного доверия.
- [Taste Skill](https://github.com/leonxlnx/taste-skill) - MIT: `npx skills add https://github.com/Leonxlnx/taste-skill --skill design-taste-frontend`. Требуются Node 22+ и Chrome/Edge/Chromium; поиск изображений может обращаться к сети.
- [UI UX Pro Max](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill) - MIT: `npm install -g ui-ux-pro-max-cli`, затем `uipro init --ai codex`. Для локального поиска нужен Python 3.x.

Это **примеры команд для оператора, а не команды, которые Toolkit запускает сам**. Codex CLI и Claude CLI для установки не требуются. Отдельная проверка точной версии и контрольных сумм нужна для подтверждения неизменности оригиналов; команды npm/npx, выбирающие последние версии, такой гарантии не дают.

После установки можно безопасно проверить наличие файлов в целевом проекте:

```text
python scripts/validate_ux_ui_orchestra.py --inspect-originals /path/to/project
```

Проверяются `.agents/skills/impeccable`, `.agents/skills/design-taste-frontend`, `.agents/skills/ui-ux-pro-max`. `FILES_PRESENT_UNATTESTED` подтверждает только структуру и локальный хеш. Это не проверка происхождения, активации в Codex Desktop или выполнения скилла. Для режима `ALL_THREE` нужны наблюдаемые записи о вызовах всех трёх. Без них нельзя утверждать, что итоговый дизайн готов к визуальному согласованию. Правила честных изображений, проверки подходящих экранов и решения владельца остаются прежними.
