# Project & Delivery Management: от PRD к проверяемым задачам

[English](../PROJECT_DELIVERY_MANAGEMENT.md) | [Product Discovery](PRODUCT_DISCOVERY.md) | [Каталог навыков](SKILLS_CATALOG.md)

**Product Discovery** отвечает на вопрос «Что и зачем создавать?». **Delivery Management** - «В каком порядке работать, что блокирует задачи и что действительно проверено?». **Engineering** реализует функцию, **QA** проверяет результаты, **Release Safety** контролирует разрешения на выпуск. Навык не устанавливает отдельный менеджер задач и не управляет агентами.

## Без терминала

В клиенте, который умеет читать Toolkit, напишите:

> Используй https://github.com/MikeMoore1337/ai-development-toolkit и мой текущий PRD. Составь короткий план задач по порядку, укажи зависимости, риски, проверки результата и одно следующее действие. Не изменяй файлы и не создавай GitHub Issues.

Если PRD нет, опишите идею своими словами. Недостающие сведения обозначаются как неизвестные, решения за владельца не придумываются. Ссылка на GitHub собственного локального проекта необязательна. Если клиент не умеет читать репозиторий, можно предоставить ему текст навыка; это не означает, что навык был автоматически активирован.

Новичок получает понятные шаги и условия готовности. Специалист - связь задач с R-ID/AC-ID, типы зависимостей, матрицу рисков, учёт изменений, доказательства и передачу работы. Правила проверок и разрешений одинаковы. [Синтетический пример](../../extensions/management/skills/project-delivery-management/references/EXAMPLES.md) использует учёт домашних расходов R1-R3 / AC1-AC4.

## Необязательная установка

Существующий Skill Manager поддерживает предварительный просмотр без изменений и явное `--apply`:

```bash
python scripts/skill_manager.py catalog --profile project-delivery-management
python scripts/skill_manager.py install --target /path/to/project --profile project-delivery-management
# Только после просмотра и разрешения:
python scripts/skill_manager.py install --target /path/to/project --profile project-delivery-management --apply
```

В профиль входят `project-delivery-management`, `task-scoping`, `requirements-traceability` и `quality-gate-assessment`. Второго контроллера нет. Необязательная проверка разрешённого JSON-плана, хранящегося **вне Toolkit**: `python scripts/validate_delivery_plan.py /path/to/plan.json`. Скрипт только читает файл и ищет структурные ошибки, разрывы связей, блокеры и циклы. Подлинность GitHub/CI/deployment-доказательств он не подтверждает.

## Статусы, ограничения и дальнейшая работа

Если в проекте используется GitHub, источником истины остаются Issues и PR. Закрытый PR не равен `MERGED`; зелёный CI не равен `RELEASED`. При недоступности GitHub указывается дата снимка и отсутствие текущей проверки. Для частных проектов без GitHub план возвращается в чат. При использовании Toolkit в чужом проекте все копии Toolkit **только для чтения**: планы, логи и отчёты в них не записываются. Файлы в проекте пользователя создаются только по явному запросу и с разрешения.

Business/System Analysis #55 получает исходные идентификаторы требований и нерешённые вопросы. UX/UI #56 получает сценарии и ограничения взаимодействия. Навык управления поставкой не придумывает их вместо профильных специалистов.
