## Релизные и технические проверки

Для согласованности инвентаря (CI) выполните `python scripts/validate_provenance.py --mode inventory --report /path/to/report.json`. Для обязательной **предпубликационной проверки** конкретного релизного дерева - `python scripts/validate_provenance.py --mode release`. Вторая команда отклоняет `owner_gate` / `excluded`, `restricted`, `unknown`, `requires_owner_review`. Для одобренного владельцем снимка она должна завершаться `PASS`, если разрешения и байты совпадают; изменения, отсутствие либо добавление файлов с ограничением, а также неверное решение владельца ведут к ошибке. **PASS не разрешает самостоятельно выпускать релиз.** Проход инвентаризации в CI также не является разрешением.

Процесс выпуска запускает проверки при отправке тегов, после публикации и при ручной проверке архива. Однако проверки GitHub `release:published` выполняются **после публикации** и не способны задним числом отменить созданный релиз. Проверки при отправке тега и обязательное согласие владельца должны предшествовать публикации. Защита ветки и права на выпуск отдельно настраиваются администратором. Реестр контрольных сумм доказывает целостность байтов и полноту состава, но **не** наличие прав. Уже выпущенные теги и архивы намеренно не изменялись.

Обязательная матрица PR на Linux/Windows запускает **оба** режима - `--mode inventory` и `--mode release` - и прикладывает машиночитаемые доказательства. Шаг Ubuntu 3.12 также экспортирует кандидат-коммит через `git archive` в чистый каталог и проверяет *контрольные суммы архивного дерева* и ограничения происхождения. Это структурная предпубликационная регрессионная проверка, **не** доказательство скачивания будущего ZIP с GitHub. Опубликованный GitHub ZIP проверяется отдельно.

Отправка нового тега без валидатора происхождения получает `BLOCKED`; проверка старых релизов без валидатора остаётся `NOT_VERIFIED`. Статусы решения владельца (`kind`, `origin`, `license`, `status`, `distribution`) закреплены вместе со списком SHA256. Подмена статуса адаптированного или распространяемого материала на `original` либо `verified` не позволяет обойти ID1337. Символьные ссылки, ошибочные типы JSON, изменённые или новые файлы под защищёнными путями отклоняются.

GitHub не может запретить пользователю с повышенными правами выпустить релиз только потому, что после отправки тега запускается workflow: **проверка и разрешение до тега обязательны**. Автономный валидатор проверяет расхождения реестра, ограничения путей, допустимые статусы/типы, описание источников, заявленные SPDX-лицензии, конфликты заголовков, уведомления, ревизии и недостоверные заявления о `verified`. Он **не** удостоверяет подлинность лицензий и разрешений, трудовые договоры, сходство кода, авторское право или личности правообладателей.

## Добавление новых компонентов

1. Установить *точные распространяемые файлы*, их автора и источник, а также выяснить, копировался ли код или защищённый текст, а не только идеи.
2. Указать upstream URL и неизменяемую ревизию, если доступна. Изучить лицензию и уведомления об авторских правах на этой ревизии. Для приватных материалов использовать непрозрачную несекретную ссылку вместо раскрытия содержимого.
3. Зафиксировать лицензию через подходящий SPDX-идентификатор либо `NOASSERTION`, если вопрос не решён. Указать обязательные уведомления и точный публичный файл с доказательством.
4. Для сомнительных или ограниченных материалов установить `owner_gate` либо `excluded`. Не выводить `verified` из файла LICENSE, публичного URL или заявления автора.
5. Выполнить автономную проверку инвентаря, официальный `skills-ref` при необходимости, контрольные суммы и предпубликационные проверки. Противоречивые права передавать на рассмотрение, не помещая приватные подтверждения в историю Git.
6. Получить явное согласие владельца для изменения статуса по разрешению либо исключения, указав дату и несекретную ссылку. Публикация прежней версии не разрешает выпуск будущей.

**Независимые ограничения остаются:** решение `permitted` сообщено владельцем по ID1337 и не изучалось в этом аудите. Границы разрешения Make Feature, обязательства работодателя в части QA и цепочка прав на элементы оформления не проверены. Каждый будущий релиз требует отдельного разрешения владельца на конкретный артефакт; **этот аудит не публиковал новый релиз**.

## Issue #195: проверка новых сторонних навыков при публикации

Для нового Skill с `origin=adapted` или `redistributed`, отсутствующего в зафиксированном одобрении владельца на уровне точных файлов, `validate_provenance.py --mode release` требует полный SHA исходного коммита (`EXTERNAL_RELEASE_PIN`). Лицензия `NOASSERTION` или `NONE` не считается разрешённой (`EXTERNAL_RELEASE_LICENSE`). Даже при заполнении этих полей действуют прежние ограничения одобрения владельца и контрольных сумм. Для внешнего Skill запрещено объявлять `status=verified` без полной исходной ревизии (`UNPINNED_VERIFIED_EXTERNAL`).

**Ранее принятые материалы сохраняют прежний статус:** защищённый QA Pack и другие разрешённые владельцем точные SHA-256 снимки продолжают использовать зафиксированные свойства. Исторический `NOASSERTION` не становится подтверждённой лицензией и не рассматривается задним числом как новый импорт. Эта проверка не подтверждает подлинность GitHub-коммита, реальные права на лицензию или готовность к публикации. Перед регистрацией кандидата используйте необязательный отчёт `external_skill_gate.py --review-context` только для чтения; чистый отчёт не разрешает установку или выполнение кода.
