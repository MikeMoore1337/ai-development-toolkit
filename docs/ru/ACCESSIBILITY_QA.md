# Проверка доступности интерфейсов - Accessibility QA (Issue #62)

[English version](../ACCESSIBILITY_QA.md) | [Каталог навыков](SKILLS_CATALOG.md)

Необязательный профиль accessibility-qa использует один специализированный навык accessibility-testing и существующие test-analysis-design, playwright-testing, quality-gate-assessment. Это проверка реализованного интерфейса, а не второй процесс проектирования, браузерный движок или сертификат WCAG. Для автономного примера не нужны платные API, браузер и внешние сервисы.

## Как начать бесплатно и без терминала

Можно написать AI-помощнику:

> Проверь, смогут ли люди пользоваться моим сайтом с клавиатуры, при увеличенном тексте и с экранным диктором. Выдели главные сценарии, изучи доступные материалы, используй бесплатный Toolkit. Ничего не меняй без разрешения и разделяй проведённые и ещё необходимые проверки.

Доступность - возможность пользоваться интерфейсом при разных способах восприятия и ввода. WCAG - рекомендации W3C по доступности веб-контента. Уровень A содержит базовые критерии, AA - дополнительные требования, AAA - более строгие рекомендации. AAA не входит автоматически в AA. Если цель веб-проекта не указана, можно предложить WCAG 2.2 AA, но юридические обязанности зависят от конкретных норм.

Клавиатура: порядок Tab и Shift+Tab, активация, выход из диалога, возврат фокуса. Порядок фокуса должен соответствовать пользовательской задаче, а фокус не должен закрываться фиксированными панелями. У поля должна быть программно доступная подпись; ошибки нужно связать с полем и объяснить словами. Видимый текст не всегда совпадает с доступным названием элемента для экранного диктора.

Контраст нарушается, когда итоговые цвета текста и фона слишком близки. Типовые пороги AA - 4.5:1 для обычного текста, 3:1 для крупного текста и применимых нетекстовых элементов, с исключениями конкретных критериев. Минимальная цель нажатия по 2.5.8 - не универсальное правило «каждая кнопка не меньше 24×24»; учитываются расстояние и исключения. Для адаптивности проверяются реальные увеличение, перестройка, длинные строки, панели и экранная клавиатура.

Автоматический анализ находит лишь часть проблем. Успешный скриншот не проверяет клавиатуру, видимое уведомление не доказывает объявление экранным диктором, а HTML не подтверждает состояние браузера. Реально проверяйте важные сценарии с клавиатуры и, где применимо, NVDA, VoiceOver или TalkBack. Фиксируйте ОС, браузер, технологию, наблюдение и ограничения. JAWS не обязателен.

## Запрос для специалиста

> Подготовь Accessibility QA plan по WCAG 2.2 AA для многоэкранного веб-приложения с формами, диалогами, динамическими уведомлениями, адаптивной вёрсткой и клавиатурной навигацией. Составь матрицу применимости, сценарии с R/AC, проверки браузера и экранного диктора, негативные случаи, приоритеты, доказательства, исправления и повторные проверки. Невыполненные испытания обозначай NOT_RUN, оценку соответствия - NOT_ASSESSED.

Процесс: требование -> применимый критерий -> пользовательская задача -> наблюдаемое условие -> проверка -> доказательство -> нарушение -> исправление -> регрессия. Критичность определяется нарушением сценария и наличием обходного доступного пути, а не буквой уровня WCAG.

[Контракты и протокол](../../extensions/accessibility/skills/accessibility-testing/references/CONTRACTS.md) включают клавиатуру, фокус, семантику, формы, контраст, анимации, размеры целей, масштабирование, обновления и дикторы. [WCAG 2.2](https://www.w3.org/TR/WCAG22/) - нормативный источник; [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/) - пояснения. [Рекомендации W3C по проверке](https://www.w3.org/WAI/test-evaluate/) и [выбору средств](https://www.w3.org/WAI/test-evaluate/tools/selecting/).

## Автономный пример

В `fixtures/accessibility/accessible.html` и `inaccessible.html` - два вымышленных интерфейса. Скрипт проверяет лишь ограниченную структуру HTML, ссылки ID и явно известные непрозрачные пары sRGB. Отображённые цвета, браузер, клавиатура, экранный диктор и полное соответствие WCAG не проверены.

```bash
python scripts/validate_accessibility.py
python -m unittest tests.test_accessibility -v
```

Для предотвращения регрессий сохраняйте связи с требованиями, негативные тесты и повторно проверяйте фактическое поведение после исправлений. Копии Toolkit в чужих проектах только для чтения. Отчёт по умолчанию возвращается в чате; пользовательские скриншоты, журналы, деревья доступности и файлы проекта не сохраняются в Toolkit.
