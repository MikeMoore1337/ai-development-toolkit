# Toolkit Native Memory / Handoff (#433)

Toolkit поддерживает **ручные пакеты передачи контекста между AI-клиентами, поиск по точной задаче Issue и явное сохранение проектных ссылок на решения** через существующие механизмы Git checkpoint, файловой записи и Project MCP. ECC, `ecc-universal`, `ecc-memory-mcp`, отдельные службы и платные API не нужны. Это не семантическая память #338 и не автоматическая передача между клиентами.

## Что реализовано

Утилита [#374 Git checkpoint](../../scripts/session_handoff_checkpoint.py) поддерживает `capture-handoff` и `verify-handoff`. Пакет JSON v2 содержит ссылку на GitHub Issue, до восьми ссылок на Issue/PR **того же проекта**, клиента-отправителя, клиента-получателя, фиксированное следующее действие и контрольную точку Git. Произвольный текст, диалоги, секреты, исходные подсказки и переписки не собираются и не включаются.

Каждый пакет имеет `trust=UNREVIEWED` и `owner_approval=NOT_GRANTED`. SHA-256 обнаруживает случайное изменение пакета, но **не подтверждает автора и не защищает от сознательной подделки**: хеш можно пересчитать. Успешная проверка означает только совпадение локального репозитория, ветки, коммита и отслеживаемого Git-состояния. На другой машине путь репозитория меняется, поэтому `repo_id` станет устаревшим, а не ложноположительным PASS. Перед продолжением сверяйте исходные GitHub Issue/PR.

## Добровольное использование

Выберите существующий каталог **за пределами репозитория** и абсолютный путь к файлу без символических ссылок в родительских каталогах:

```sh
python scripts/session_handoff_checkpoint.py capture-handoff --repo /path/to/project \
  --issue https://github.com/OWNER/REPO/issues/123 \
  --from-client codex --to-client hermes \
  --ref https://github.com/OWNER/REPO/pull/124 \
  --next-action REVIEW_PR --file /path/to/external/handoff.json

python scripts/session_handoff_checkpoint.py verify-handoff --repo /path/to/project \
  --to-client hermes --file /path/to/external/handoff.json
python -m unittest discover -s tests -p test_session_handoff_checkpoint.py -v
```

Файл создаётся **только по явному действию**, без перезаписи; на POSIX права 0600. Получатель самостоятельно запускает проверку и открывает ссылки. Возможные действия: `REVIEW_ISSUE`, `REVIEW_PR`, `RUN_TESTS`, `CHECK_CI`, `WAIT_FOR_OWNER`, `NONE`. Чужой проект, неверный получатель, изменение файла, устаревший Git, символическая ссылка и повреждённые данные отклоняются. В локальном репозитории должен быть `origin` GitHub (HTTPS или SSH), совпадающий с проектом Issue. Отсутствующий или подменённый `origin` блокирует передачу без сетевых запросов. Откат - удалить только созданный файл. Никаких изменений пользовательского AGENTS.md, MCP, хуков, общей памяти и фоновых задач.

- #374 сохраняет прежние `capture/verify` без изменения их формата.
- Источники истины - GitHub Issue/PR и утверждённая документация; handoff не является инструкцией или разрешением.
- [Историческая CI-проверка исходного ECC](../../.github/workflows/ecc-memory-vault.yml) выполняет оригинальные команды в одноразовой среде, но **для пользователя Toolkit ECC не требуется**.

Код этой реализации - расширение существующего Python-механизма Toolkit, без копирования ECC. Не используются Codex CLI, Claude CLI, платные API и дополнительные расходы.

## Нативный поиск по точной задаче Issue (#433)

В существующей утилите доступен **ручной поиск без записи** по ранее созданным пакетам handoff в выбранном каталоге **за пределами Git-репозитория**. Отдельная база, подключение ECC, глобальная индексация, сбор переписок и фоновая синхронизация не нужны. Поиск выполняется строго по ссылке GitHub Issue и клиенту-получателю, не по естественному языку:

```sh
python scripts/session_handoff_checkpoint.py search-handoffs --repo /path/to/repo --directory /path/to/external/packets --issue https://github.com/OWNER/REPO/issues/123 --to-client hermes
```

Допускается не более 16 небольших JSON-файлов со строгими именами. Символические ссылки, необычные расширения, посторонний проект GitHub, подменённая контрольная сумма, повреждённая структура, дубли и хранение внутри репозитория блокируют поиск. `PASS` возможен только после штатной проверки целостности v2, соответствия проекта/получателя и неизменённого состояния Git. Для устаревших пакетов возвращается `git_check=STALE`, но ссылки и следующее действие **не выдаются**. При отсутствии подтверждённых результатов выводится `REVIEW_REQUIRED`, а не ложный успех. Отчёт содержит только известные публичные ссылки Issue/PR, хеш, фиксированное действие и статусы, без локальных путей и имён файлов.

**Ограничения:** это поиск структурированных ссылок, а не семантическая память, подтверждение автора, утверждённая человеком практика или межмашинная синхронизация. #338 Episodic Memory остаётся отдельной функцией. Нативный запуск в Codex Desktop/Hermes не подтверждён; задача #433 остаётся открытой.

## Нативный интерфейс передачи контекста через Toolkit Project MCP (#433)

Существующий добровольно подключаемый Project MCP Toolkit получил два **инструмента чтения без записи**, для которых не требуется ECC Memory Vault или отдельный MCP:

- `toolkit_search_handoffs`: `project` (точный абсолютный корень Git), `directory` (явный существующий каталог вне проекта), `issue_url` (Issue того же GitHub-репозитория), `to_client` (получатель). Использует существующий `search_handoffs` с ограничением 16 пакетов, проверкой целостности и устаревшего состояния Git.
- `toolkit_verify_handoff`: `project`, `file` (точный абсолютный путь к JSON-пакету вне проекта), `to_client`. Использует ранее реализованный `verify_handoff`; не создаёт новые файлы и не меняет репозиторий.

Инструменты доступны только **после явного подключения Toolkit Project MCP пользователем** и отдельного вызова клиентом. Сервер не сканирует домашнюю папку, не собирает переписку, не синхронизирует устройства, не запускает фоновые службы и не обращается к GitHub по сети. Статусы `trust=UNREVIEWED` и `owner_approval=NOT_GRANTED` не повышаются по совпадению SHA-256; это не подтверждение автора и не разрешение выполнить команду. Устаревший пакет не возвращает ссылок и следующего действия. Вложенные Git-каталоги, чужие Issue, дополнительные параметры, символические ссылки и испорченные пакеты отклоняются. Платные API и агенты CLI не используются.

**CI на исходниках не доказывает обнаружение инструментов в Codex Desktop и реальный Codex→Hermes→Codex handoff.** Хранение вручную выбранных ссылок на решения реализовано ниже, но `--operator-reviewed` - лишь заявление оператора, а не удостоверенное согласование. Семантическая память #338, аутентифицированная передача и отдельно разрешённый релиз остаются за рамками этой поставки. Откат - отключение Project MCP или возврат соответствующей ревизии Git.

## Формирование пакета в памяти через Project MCP (#433)

Третий инструмент Project MCP `toolkit_prepare_handoff` **не выполняет запись**: он формирует полноценный нативный пакет v2 и возвращает его в поле `packet`. Обязательные параметры: точный абсолютный корень Git `project`, принадлежащий этому репозиторию `issue_url`, идентификаторы `from_client` / `to_client`, `references` (0–8 публичных Issue/PR того же проекта), `next_action` из фиксированного набора `REVIEW_ISSUE`, `REVIEW_PR`, `RUN_TESTS`, `CHECK_CI`, `WAIT_FOR_OWNER`, `NONE`. Произвольный текст, журналы чатов, секреты и команды shell в пакет не принимаются.

Пакет содержит `trust=UNREVIEWED`, `owner_approval=NOT_GRANTED`, SHA-256 целостности (не подпись); в ответе `packet_storage=NOT_PERSISTED`. **Project MCP не записывает пакет**, не отправляет его Hermes и не разрешает исполнение следующего действия. Сохранение за пределами Git-проекта - отдельное явное действие пользователя. Существующая команда CLI `capture-handoff` по-прежнему предоставляет create-only режим записи; клиент может впоследствии вызвать `toolkit_verify_handoff` либо `toolkit_search_handoffs`.

На синтетическом Git-репозитории тест проверяет создание пакета через MCP, отдельно инициированную запись во внешний временный каталог и чтение/поиск через MCP. Это подтверждает только совместимость исходников, **не** реальную передачу в Codex Desktop/Hermes, полномочия проверяющего или права работающего клиента. ECC, фоновые процессы и платные API не требуются.

## Ручная переносимая проверка Git-контекста (#433)

В существующем Project MCP добавлен **только для чтения** `toolkit_verify_portable_handoff` с аргументами `project`, `file`, `to_client`. Аналогичная команда в Toolkit:

```sh
python scripts/session_handoff_checkpoint.py verify-portable-handoff --repo /path/to/recipient/repository --file /path/to/manual/handoff.json --to-client hermes
```

Пользователь сам передаёт файл JSON v2 на другое устройство и явно выбирает его. Синхронизации или передачи данных по сети нет. В отличие от строгого `verify-handoff`, проверка допускает различие абсолютных путей к репозиторию, но требует совпадения GitHub `origin`, контрольной суммы, получателя, ветки, коммита и состояния отслеживаемых файлов Git. При иных расхождениях возвращается `BLOCKED` или `STALE` **без ссылок**. Даже при совпадении результат - **`REVIEW_REQUIRED`** (код CLI 2), `sender_identity=NOT_VERIFIED`, `owner_approval=NOT_GRANTED`, фиксированное действие `REVIEW_ISSUE`. Действие из исходного пакета не разрешается к исполнению. SHA-256 не удостоверяет автора. Для принятия решения нужно отдельно проверить первоисточник - Issue/PR на GitHub.

**Не реализовано одним только переносимым верификатором:** удостоверенная человеком память решений, семантический поиск (#338), аутентификация отправителя/устройства, транспорт, реальная работа Codex Desktop ↔ Hermes и публичный релиз Toolkit. Отдельные ручные записи ссылок описаны ниже, но они не подтверждают личность проверяющего или согласие владельца. Откат - отказаться от вызова нового инструмента или вернуть соответствующую ревизию. ECC, отдельный MCP, фоновые службы, платные API и настройки клиентов не меняются.

## Записи памяти с указанием проверенного человеком решения (#433)

Используется существующий механизм ручного сохранения JSON-файлов с запретом перезаписи: `scripts/reviewed_memory.py`. **Новой базы, ECC, MCP-сервера или второго семантического хранилища нет.** Пользователь сначала изучает решение в GitHub Issue/PR и затем отдельно создаёт проектную запись: URL задачи, точная ссылка на комментарий или проверку PR, тип `DECISION`/`PRACTICE`/`LIMITATION`, однострочная сводка 8-240 символов и до восьми публичных ссылок того же репозитория. Свободный текст не исполняется; потенциальные секреты, пути, адреса электронной почты, произвольные URL, переносы строк и ссылки на чужой проект отклоняются. Запись внутри Git-репозитория и перезапись существующего файла запрещены.

```sh
python scripts/reviewed_memory.py prepare --repo /path/to/repo --issue https://github.com/ORG/REPO/issues/123 --review-url https://github.com/ORG/REPO/issues/123#issuecomment-456 --kind DECISION --summary "Manual review chose the existing integration path."
python scripts/reviewed_memory.py record --repo /path/to/repo --issue https://github.com/ORG/REPO/issues/123 --review-url https://github.com/ORG/REPO/issues/123#issuecomment-456 --kind DECISION --summary "Manual review chose the existing integration path." --file /external/manual-memory/decision-123.json --operator-reviewed
python scripts/reviewed_memory.py search --repo /path/to/repo --directory /external/manual-memory --issue https://github.com/ORG/REPO/issues/123
```

`prepare` ничего не сохраняет. Только отдельная команда `record --operator-reviewed` создаёт новый файл. В существующем Project MCP появились три инструмента **только для чтения**: `toolkit_prepare_reviewed_memory`, `toolkit_read_reviewed_memory`, `toolkit_search_reviewed_memory`. Они формируют предварительную запись и находят её по точной задаче во вручную выбранной внешней папке (не более 16 файлов). Идентификатор проекта основан на GitHub-репозитории, а не на локальном пути, поэтому отдельный файл можно вручную перенести на другое устройство. Удаление конкретного файла удаляет запись. Фонового сканирования личной памяти и автоматической передачи нет.

**Ограничения:** флаг `--operator-reviewed` фиксирует **заявление оператора**, но не аутентифицирует человека и не доказывает просмотр комментария. Ссылка на ревью не проверяется через сеть, SHA-256 - не цифровая подпись. Поэтому чтение и поиск всегда возвращают `REVIEW_REQUIRED`, `trust=UNTRUSTED_REFERENCE`, `review_attestation=NOT_VERIFIED`, `owner_approval=NOT_GRANTED`. Никаких команд из памяти не выполняется. Это поиск точных проектных решений, не семантическая память #338 и не источник правил. Передача между клиентами, проверка личности автора, реальная приёмка Codex Desktop ↔ Hermes и публичный релиз Toolkit всё ещё **не подтверждены**.
