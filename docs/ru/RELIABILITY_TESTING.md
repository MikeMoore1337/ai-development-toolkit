# Тестирование отказоустойчивости (Issue #58)

[English version](../RELIABILITY_TESTING.md) | [Навык](../../extensions/reliability/skills/reliability-testing/SKILL.md)

Надёжность подтверждается сохранением проверяемых свойств системы при
сбоях, а не самим фактом наличия повторных попыток. Сначала задайте
бизнес-инвариант, затем точку отказа, управляемое воспроизведение,
проверку сохранённого состояния и восстановление. Необязательный профиль
`reliability-testing` не устанавливает весь QA Pack и не создаёт контроллер.

## Основные понятия

- **Timeout** не доказывает, что операция не выполнена. Запись могла
  сохраниться, а ответ - потеряться. Результат вызова остаётся неизвестным
  до проверки состояния или согласования результата.
- **Retry** повторяет запрос, а **idempotency** препятствует недопустимому
  повторному эффекту. Ограничивайте попытки, общий бюджет и задержку;
  ошибки доступа и операции без безопасного ключа не повторяйте вслепую.
- **Race condition** - результат зависит от порядка конкурирующих операций;
  потеря изменения возникает при записи из устаревшего состояния.
  Управляемый порядок воспроизводит конкретную гонку, но не доказывает
  отсутствие всех других.
- **At-least-once** допускает повторную доставку. Даже атомарная
  дедупликация и подтверждение после сохранения результата не доказывают
  **end-to-end exactly-once** для внешних эффектов.
- **Частичная транзакция** возникает при сбое между связанными изменениями.
  Проверяйте commit/rollback на реальном хранилище, когда оно доступно.
- **Recovery** подтверждается проверкой сохранённых данных, ключей
  событий и незавершённых операций, а не одним запуском процесса.
  Статусы: RECOVERED, RECOVERY_PENDING, RECOVERY_BLOCKED, STATE_UNKNOWN.

## Матрица повторного использования

| Свойство | Что уже есть | Дополнение и решение |
| --- | --- | --- |
| Timeout | `background-processing`, `integration-testing` | NEW: отказ до/после эффекта и проверка состояния |
| Retry и backoff | `background-processing` | REFINE: лимит попыток и виртуальные задержки |
| Идемпотентность | `background-processing` | NEW: проверка итогового бизнес-эффекта после повтора |
| Конкурентные изменения | `database-validation`, `integration-testing` | NEW: управляемые lost update и конфликт версий |
| Частичные транзакции | `database-validation`, `integration-testing` | NEW: прерывание после первого изменения и откат |
| Дубликаты событий | `background-processing`, `contract-testing` | NEW: инвариант общего результата, а не только маркера |
| Нарушение порядка | `contract-testing`, `background-processing` | NEW: проверка монотонности версии |
| Восстановление | `background-processing`, `failure-triage` | REFINE: повторное открытие SQLite и проверка ключа |
| Управляемые отказы | Общая методика QA | NEW: ограниченные точки отказа и расписания |
| Доказательства надёжности | `failure-triage`, `quality-gate-assessment` | NEW: контракт сценария и проверяемого результата |

Новый навык дополняет имеющиеся методики, не создавая второй обработчик,
брокер или управляющий процесс.

## Проверки без доступа к сети

В разрешённой рабочей копии Toolkit:

~~~sh
python scripts/validate_reliability.py
python scripts/validate_reliability.py --json
python -m unittest tests.test_reliability -v
~~~

Девять автономных сценариев проверяют повтор события, таймаут после
записи, потерю обновления, откат транзакции, ограниченные попытки,
устаревшее событие, подтверждение до commit, повторное открытие SQLite
и конфликт версий. Девять заведомо неверных вариантов должны быть
отклонены **теми же** проверками состояния. Внешних API, расходов,
случайных задержек и production-тестов нет. Эта модель **не доказывает**
долговечность реального сервера, отсутствие всех гонок, свойства
настоящего брокера, exactly-once или фактическую доступность.

**Для новичка:** «Проверь, не потеряются ли мои данные при повторных
запросах, остановке сервера и одновременном изменении. Начни с безопасных
локальных проверок и покажи, что осталось непроверенным».

**Для специалиста:** «Подготовь модель at-least-once, dedup,
ack-after-commit и recovery после restart. Зафиксируй контролируемые
порядки операций, инварианты, независимые проверки состояния и пределы
выполнения. Свойства реального брокера сообщений пометь как NOT_MEASURED,
пока они не подтверждены отдельным испытанием».

Повторно используются background-processing, integration-testing,
database-validation, contract-testing и failure-triage. Toolkit и его
копии остаются источниками только для чтения в чужих проектах;
результаты по умолчанию возвращаются в чат. Запись файлов - только
в отдельно разрешённое место.
