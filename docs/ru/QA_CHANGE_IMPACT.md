# Выбор регрессионных проверок по изменениям (read-only)

[English version](../QA_CHANGE_IMPACT.md)

Вспомогательная команда реализует **планирование проверок** на основе [Change Impact Analysis](../../extensions/qa/skills/change-impact-analysis/SKILL.md), [Requirements Traceability](../../extensions/qa/skills/requirements-traceability/SKILL.md) и [Quality Gate Assessment](../../extensions/qa/skills/quality-gate-assessment/SKILL.md). Это **не** второй QA-раннер, полный граф вызовов, обязательный CI-gate или замена правил выпуска проекта.

## Использование без платных API

Передать изменённые относительные пути:

```bash
python scripts/qa_change_impact.py --paths frontend/views/Workout.tsx backend/api/schema.py db/migrations/101.sql
```

Или взять изменённые файлы из локального Git между **двумя полными 40-символьными SHA** в репозитории, к которому есть разрешённый доступ:

```bash
python scripts/qa_change_impact.py --root /path/to/repo --repository org/repo --git-base BASE_40_SHA --git-head HEAD_40_SHA
```

Для Windows указывайте локальный путь к репозиторию в формате Windows. Команда не скачивает репозиторий, не вызывает модель, не устанавливает навыки и не запускает pytest/Playwright. `--output report.json` создаёт **новый** отчёт без перезаписи существующих доказательств. Не передавайте клиентские персональные данные или секреты в аргументах.

## Что действительно проверяется

По токенам имён файлов выбираются условные категории AUTH, PRIVACY, API, DB, UI, ASYNC, CI. Документы Markdown/RST/MDX/AsciiDoc получают отдельную рекомендацию `documentation-review`, без безусловного `targeted-unit`; при смешанном PR документы не считаются исполняемым кодом. Для файлов тестов добавляется `test-review`. Имена `server.py`, `http`, `routes` и каталог `web/` дают **эвристические** подсказки API/UI, но не подтверждают их реальные контракты. Изменение авторизации требует проверить запреты и изоляцию пользователей; миграция БД - целостность и откат; совместные UI/API-изменения - ограниченный сквозной сценарий. Для неизвестных файлов предусмотрена **обязательная ручная оценка** влияния вместо статуса готовности.

Каждая рекомендация содержит изменённые пути, обоснование, риск и статусы `NOT_RUN`, `PATH_HEURISTIC_ONLY`, без выдуманных логов и команд фактического запуска. Даже при сверке точных Git SHA проверяются только имена файлов, а не реальные вызовы, содержимое контракта, доступность тестов, критерии приёмки или состояние production. Поэтому инженер обязан изучить diff, реальных потребителей, требования Issue, правила `AGENTS.md` и при необходимости расширить проверки. Результат не отменяет существующий CI или разрешения владельца.

`fixtures/qa_change_impact_cases.json` содержит **синтетические** примеры PR для разных типов приложений. Их успешный прогон не является проверкой настоящих проектов.

## Подсказки по QA на основе каталога (Issue #278)

У каждой предложенной проверки появился объект `guidance`: **рекомендуемый профиль**, **навык** и **предполагаемый тестовый сценарий**. Все пары профилей и навыков объявлены в `MANIFEST.json`; эти рекомендации не устанавливают навыки и не запускают тесты. Например: AUTH — `qa-security` / `security-testing` (запрет чужого доступа), API — `qa-contract` / `contract-testing`, DB — `data-engineering` / `database-validation`, UI — `qa-ui` / `playwright-testing`, ASYNC — `reliability-testing` / `background-processing`, PRIVACY — `qa-security`, CI — `devops-infrastructure` / `release-safety`.

Маркер `source=STATIC_MANIFEST_CATALOG_HINT` означает **рекомендацию по исходникам**, а не проведённую проверку. Статусы `client_skill_activation=NOT_VERIFIED`, `test_execution=NOT_RUN` и `test_command=null` сохраняются. Для неизвестного файла предлагается `change-impact-analysis` с необходимостью определить подсистему, а не выдуманный тест и не разрешение на релиз. Те же подсказки получают проверки, добавленные при ограниченном анализе diff: важные первоначальные проверки не исключаются. Зависимые потребители, вызовы функций и PASS не выводятся из совпадения пути.

## Признаки изменения сохранённого состояния и зависимых компонентов

При `--inspect-diff` содержимое документационных файлов не используется для выводов о runtime API/auth/DB: упоминание термина в README не равно изменению реализации. Добавленные или удалённые маркеры `mutation_id`, `expected_version`, `request_fingerprint`, `is_completed` и присваивания версии создают сигнал **PERSISTED_STATE**. Он добавляет `state-integrity` (версии, целостность данных и отсутствие пустых записей), `async-replay` (идемпотентность, повторы, конфликты), `consumer-review` (ручной поиск вызывающих компонентов). Признаки API также добавляют `consumer-review`. Совпадение токена **не доказывает** наличие графа вызовов, миграции БД, известных потребителей или выполненных тестов.

Например, изменение сохранения подхода может затронуть неизменённые HTTP PATCH, сервис прогрессии и офлайновую очередь frontend. Такие компоненты проверяются **вручную** с последующей привязкой тестов и критериев приёмки по согласованной карте. Возможны ложноположительные срабатывания: изменение версии в коде само по себе не означает миграцию или откат БД. Все проверки остаются `NOT_RUN` до реального выполнения.

## Ручная передача QA

Заполнить связку `изменённый файл → потребитель/контракт → риск → конкретный тест → оракул → статус → ссылка на результат`. Для сложных изменений использовать существующую QA Orchestra и трассируемость требований. Статус PASS/FAIL можно указать только после реального запуска теста на конкретном SHA и в известной среде.


## Необязательная связь с тестами и требованиями проекта

Если в проекте уже ведётся список тестов и критериев приёмки, можно передать **отдельно проверенную** JSON-карту:

```bash
python scripts/qa_change_impact.py --paths frontend/views/workout.tsx backend/api/schema.py --test-map fixtures/qa_change_impact_test_map.json
```

Формат версии 1 содержит `entries` со строгими полями `id`, `prefix` (путь к директории, например `frontend/views/`), `check_ids` (существующие категории QA), `test_ids` (идентификаторы тестов) и `requirement_ids` (идентификаторы требований проекта). Выбираются только точные префиксы каталогов. Регулярные выражения, shell-команды, исполняемые хуки, сетевые загрузки и выдуманные автоматически ID не допускаются.

В отчёте `declared_test_candidates` содержит привязку к ID теста и требования, исходные изменённые файлы и только `NOT_RUN` / `OWNER_DECLARED_NOT_VERIFIED`. Поле `unmapped_check_ids` показывает рекомендованные проверки, **для которых нет записанного теста**. Наличие ID в карте не подтверждает существование теста, его релевантность или успешное исполнение. Карта не отменяет ни одну критическую проверку из первоначального плана.

`fixtures/qa_change_impact_test_map.json` - **исключительно синтетический пример**: содержащиеся в нём тесты и требования не являются реальными фактами о действующих приложениях. В настоящем проекте карту согласует владелец; инженер проверяет исходные тесты, фактический diff, acceptance criteria и правила выпуска. Никаких платных API и самостоятельных изменений проекта.


## Необязательная проверка изменённых строк кода

Для локального репозитория, в котором доступны два **полных Git SHA**, можно включить ограниченный анализ текстового diff:

```bash
python scripts/qa_change_impact.py --root /path/to/repo --git-base BASE_40_SHA --git-head HEAD_40_SHA --inspect-diff
```

Используется стандартный Git diff без внешних diff-команд, textconv, цвета и распознавания переименований. Ограничение: **256 КиБ** UTF-8 patch. Анализируются узкие признаки в добавленных или удалённых строках - объявления API, авторизация, SQL-миграции, состояние UI, фоновые задачи, приватные данные и деплой. В отчёт выводятся **только количество строк и названия категорий**: исходные строки, значения и секреты не показываются. Бинарные и неопознанные файлы требуют ручной проверки. Большой, невалидный или некорректно декодируемый diff блокируется.

Раздел `diff_content` честно помечен `LOCAL_PATCH_TOKEN_HINTS_ONLY`. Сигналы могут **добавить** рекомендованные тесты, но не снимают предыдущие требования, не подтверждают CI и не разрешают деплой. Статусы остаются `NOT_RUN`, итоговый gate - `INSUFFICIENT_EVIDENCE`, ID тестов из карты - `OWNER_DECLARED_NOT_VERIFIED`. Даже при обнаружении SQL-токена нет доказательства, что реальная миграция требуется, все потребители известны или изменение безопасно.

`--inspect-diff` недоступен с `--paths`: список файлов не предоставляет подтверждённого содержимого патча. Инструмент не является полным парсером кода, графом вызовов, аудитом безопасности или тестовым раннером. Использовать только на коде, к которому имеется разрешённый доступ.
