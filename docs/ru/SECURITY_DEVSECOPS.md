# Security Engineering и DevSecOps (Issue #60)

[English source](../SECURITY_DEVSECOPS.md)

**Цель:** связать реальные активы, границы доверия, гипотезы угроз, реестр рисков и проверяемые защитные меры. Это не сканер, не сертификат, не пентест и не проверка реальных моделей ИИ. Необязательный профиль `security-engineering` использует существующие `security-boundaries`, `security-review`, `security-testing`.

## Начать без опыта
**«Проверь безопасность моего приложения. Сначала найди реальные активы, границы доверия и главные риски. Объясни простыми словами. Начни с анализа без изменений, не трогай чужие серверы, не используй платные сервисы».**

Для специалиста: **«Подготовь модель угроз с матрицей субъект-ресурс-действие, изоляцией арендаторов, границами CI, жизненным циклом секретов, происхождением зависимостей и независимыми негативными тестами. Отмечай отсутствие доказательств».**

Результаты по умолчанию возвращаются в чате. Если Toolkit используют в другом проекте, его источники остаются только для чтения; чужие отчёты, секреты и исходники в него не сохраняются.

## Порядок анализа
1. Найти реальные активы, участников, потоки данных, точки входа и границы доверия.
2. Записать условия, возможное нарушение и доказательства для каждой угрозы. Гипотеза угрозы не равна найденной уязвимости.
3. Связать Threat ID -> Risk ID -> Control ID -> негативный тест. Для каждого правила определить разрешённое ALLOW, запрещённое DENY и отсутствие нежелательных изменений.
4. Выполнять только разрешённые испытания в изолированной среде. Запрос пользовательских данных из чужого tenant должен отклоняться, даже если клиент подставил чужой owner ID. Истёкшая сессия также не даёт доступа.
5. Находка -> оценка риска -> минимальное исправление -> негативная регрессия -> сохранение законного ALLOW -> остаточный риск и решение владельца.

**Authentication** подтверждает личность. **Authorization** проверяет право этой личности на конкретный ресурс. **Tenant isolation** разделяет области данных разных владельцев. Скрытая кнопка на фронтенде не заменяет проверку на доверенной стороне.

## Секреты, CI, цепочка поставки
Проверяйте создание, хранение, передачу, использование, ротацию, отзыв, удаление и реагирование на компрометацию секретов. Не выводите реальные значения токенов в отчёты и логи. CI должен учитывать запросы от внешних участников, минимальные разрешения, недоверенный ввод в shell, версии Actions, скачиваемый код и происхождение артефактов.

Для зависимостей фиксируйте версию, источник, назначение, прямое/транзитивное использование, лицензию или `UNKNOWN`, проверенные рекомендации безопасности или `VULNERABILITY_STATUS=NOT_CHECKED`. **Контрольная сумма** показывает только совпадение байтов с ожидаемыми; **происхождение**, **подлинность издателя**, **права распространения** и **безопасность** проверяются отдельно. SBOM в SPDX или CycloneDX необязателен; неполный список прямых зависимостей нельзя выдавать за полный состав.

Статический анализ не доказывает практическую эксплуатацию. Синтетические тесты не подтверждают безопасность реального сервиса. Отсутствие находок не гарантирует отсутствие уязвимостей.

## Автономный пример
`python scripts/validate_security.py` и `python -m unittest tests.test_security_engineering -v`: десять пар исправной и намеренно неисправной реализации. Независимый oracle должен принять исправные и отвергнуть все десять дефектов: чужое чтение, подмену владельца, изменение перед отказом, утечку секретного маркера, выход инструмента за каталог, отсутствие подтверждения, избыточные права CI, ложное происхождение, неверную SHA256 и неотредактированный отчёт. Без сети, реальных ключей и платных API.
