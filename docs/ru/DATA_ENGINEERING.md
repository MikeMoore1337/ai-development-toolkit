# Инженерия данных и аналитика (Issue #65)

[English source](../DATA_ENGINEERING.md)

Опциональный профиль data-engineering содержит один новый навык и переиспользует существующие Backend, QA и Reliability. Он не требует собственного ETL-движка, оркестратора, DWH, брокера, BI, платных API или отдельной платформы.

## Основные понятия

- ETL - извлечение, преобразование, загрузка. ELT - извлечение, загрузка, затем преобразование в целевом хранилище. Выбор зависит от местонахождения данных, приватности, доступных ресурсов, объёма, задержки и стоимости.
- Data Contract - согласованный смысл набора данных, ключей, полей и типов, производителя, потребителей, версий, приватности и временных отметок. Это не физическая схема базы и не бизнес-требование.
- Data Quality - полнота полей И партий, валидность по контракту, согласованность единиц/связей, уникальность ключей, свежесть по времени события и наблюдения и точность относительно независимого эталона. Валидность не доказывает фактическую точность.
- Schema Evolution - проверка совместимости источников и потребителей, включая изменение смысла без смены типа. Добавление nullable-поля не гарантирует совместимости со строгими потребителями.
- Data Lineage - происхождение из набора/версии, партии, преобразования/версии и выходного набора. Неполные связи помечаются PARTIAL, не придумываются. Lineage само по себе не удостоверяет подлинность источника.
- Incremental Processing - подтверждение checkpoint только после успешной записи, стабильные идентификаторы партий, безопасные повторы и поздние события. Локальная дедупликация не доказывает внешнюю гарантию exactly-once.
- Backfill - план, разрешённое выполнение и независимое подтверждение исправления являются разными этапами. Без идемпотентности повтор способен удвоить результат.
- Analytics Metric - явные формула, числитель/знаменатель, детализация, окно, часовой пояс, NULL, нулевой знаменатель, фильтры, округление. Бизнес определяет смысл, инженер рассчитывает, QA независимо проверяет.

## Анализ пробелов и переиспользование

| Возможность | Существующие навыки | Новое в #65 |
| --- | --- | --- |
| Хранение, транзакции, целостность | `data-access`, `database-validation` | Без дублирования |
| Контракты, потребители, миграции | `contract-testing`, `database-migrations` | Версии и совместимость конвейеров |
| Качество, тестовые данные | `test-data-management`, `integration-testing` | Полнота набора, свежесть и независимый расчёт |
| Восстановление и инциденты | `reliability-testing`, `observability-sre` | Checkpoint, поздние события, синтетический backfill |
| Бизнес-требования и метрики | `business-system-analysis`, `product-discovery` | Проверка числителя, знаменателя и результата |
| ETL/ELT и lineage | Частично покрыты смежными навыками | Один специализированный процесс от источника до результата |

Дополнительные роли, контроллер и второй QA Pack не нужны. Пример подтверждает только локальные свойства; настоящая атомарность БД требует отдельных тестов.

## Для новичка

Пример: «У меня есть Excel- и CSV-файлы. Помоги объединить их по подтверждённым ключам, проверить дубликаты, пропуски и суммы. Покажи предварительный результат без изменения исходников». Не требуется знать ETL/ELT. Для настоящих Excel-файлов в целевом проекте может потребоваться специальная библиотека, которую профиль не устанавливает.

## Для специалиста

Пример: «Спроектируй инкрементальный ETL/ELT с версиями контрактов, совместимостью схем, дедупликацией, watermark/checkpoint, поздними событиями, lineage, ограниченным backfill и независимыми проверками качества и метрик. Неизвестные свойства оставляй UNKNOWN».

## Автономная проверка

В корне Toolkit:

    python scripts/validate_data_engineering.py
    python -m unittest discover -s tests -p test_data_engineering.py -v

Три синтетические партии, включая позднее событие, и 25 заведомо повреждённых случаев. Одинаковый независимый аудитор должен принять правильный вариант и отклонить каждый неправильный. Эталонные значения заданы отдельно от расчёта конвейера; прерывание и повтор проверяются без реальной БД.

Только стандартная библиотека Python для тестов самого Toolkit, не обязательная для применения навыка в других проектах. Нет сетевых запросов, персональных данных, сторонних сервисов и расходов. Реальная устойчивость хранилища, подлинность источников, точность пользовательских данных, совместимость реальных потребителей, большие нагрузки и фактическая активация в ИИ-клиенте - NOT_TESTED/NOT_MEASURED. Синтетический PASS не доказывает production PASS. Данные и отчёты чужих проектов не сохраняются в Toolkit.
