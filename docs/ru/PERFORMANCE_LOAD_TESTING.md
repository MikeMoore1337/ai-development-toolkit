# Тестирование производительности и ограниченной нагрузки (Issue #59)

[English source](../PERFORMANCE_LOAD_TESTING.md) | [Устанавливаемый навык](../../extensions/performance/skills/performance-load-testing/SKILL.md) | [Контракт](../../extensions/performance/skills/performance-load-testing/references/CONTRACT.md)

Тестирование производительности измеряет скорость конкретной операции в
фиксированных условиях. **Нагрузочное тестирование** воспроизводит
ограниченную ожидаемую нагрузку, а **стресс-тестирование** исследует поведение
за пределами обычных нагрузок и не запускается автоматически. Проверка
отказоустойчивости при сбоях - отдельная задача.

## Что переиспользуется

| Направление | Существующий навык | Решение |
| --- | --- | --- |
| Отрисовка и взаимодействия в браузере | `frontend-performance` | REUSE, без копирования |
| Базовое измерение и сопоставимость | `frontend-performance` | REFINE, сравнение под нагрузкой |
| Модели нагрузки, частота и ограничения | `test-strategy` | NEW, проверяемый контракт |
| Задержки, процентили, пропускная способность, ошибки | QA-методики | NEW, вычисления и независимые тесты |
| Бюджеты и вариация | `frontend-performance` | REFINE, согласование и статусы |
| Использование ресурсов | `failure-triage` | REUSE, отсутствие данных видно явно |
| Узкие места | `failure-triage` и backend-навыки | REUSE, гипотеза не считается фактом |
| Повторная доставка и восстановление | `reliability-testing` | REUSE, отдельная проверка |
| Безопасность нагрузочного тестирования | `security-boundaries` | NEW, исполняемые ограничения |

Новый опциональный профиль `performance-load-testing` включает один
специализированный навык, `test-strategy` и `failure-triage`. Он не
устанавливает весь QA Pack и не управляет процессом разработки.

## Основные понятия

- **Latency** - время выполнения операции, измеренное монотонными часами.
- **Throughput** - число попыток, завершений и успехов в секунду фактического
  интервала. Настроенные 5 RPS не доказывают фактическую пропускную способность.
- **p95 / p99** - значения, ниже которых находятся примерно 95% / 99%
  наблюдений при выбранном способе расчёта. Малая выборка не характеризует
  надёжно край распределения.
- **Baseline** - исходная версия вместе с зафиксированными условиями.
- **Candidate** - новая версия при тех же входных данных, прогреве, кэше,
  настройках, среде и методике.
- **Performance budget** - заранее установленный порог, единицы, условия,
  источник и допуск. Пока владелец не согласовал значение: `PROPOSED`.
- **Вариация** - разброс измерений из-за системы, фоновых задач и кэша.
  Сохраняйте сырые данные и выполняйте повторы.
- **Функциональная корректность** - обязательна: более быстрый, но ошибочный
  результат не может считаться успешной оптимизацией.

## Полностью автономный пример

Из рабочего каталога разработки Toolkit:

```sh
python scripts/validate_performance.py --mode virtual --profile constant
python scripts/validate_performance.py --mode virtual --profile step
python scripts/validate_performance.py --mode virtual --profile mixed
python scripts/validate_performance.py --mode local --operations 5 --duration 2
python -m unittest tests.test_performance -v
```

**Virtual** использует вымышленные временные метки и предназначен только для
детерминированной проверки расчётов и решений. Это не измерение скорости
приложения. **Local** измеряет только небольшую фиктивную Python-функцию внутри
процесса, это ограниченная проверка запуска. Результаты выводятся в JSON
на экран, файлы не сохраняются. Вредоносно «ускоренный» вариант намеренно
нарушает вычисления и отклоняется независимой проверкой результата.

Ограничения: **до 5 RPS, до 50 операций вместе с прогревом, до 2 одновременных
операций, до 10 секунд**. Конфигурация проверяется до запуска. Пример не
принимает URL, не открывает сетевых соединений, не требует Docker,
облачных сервисов и платных инструментов. Он не нагружает production, VPS,
публичные сайты, чужие API или общие тестовые среды.

## Как читать результат

[Переносимый контракт](../../extensions/performance/skills/performance-load-testing/references/CONTRACT.md)
определяет идентификаторы, требование, версии, нагрузку, пределы,
исходные измерения, расчёты, ошибки, бюджет, сопоставимость, гипотезы
и подтверждённые причины, итоговый статус и ограничения. CPU/RAM в данном
примере не измеряются: `NOT_MEASURED`.

Статусы: `PASS` (ухудшение не подтверждено в этих условиях),
`REGRESSION`, `INCONCLUSIVE`, `COMPARISON_INVALID`,
`NOT_MEASURED`, `BLOCKED`. p95 выводится не менее чем по 20
завершённым операциям, p99 - по 100; следовательно, в ограниченном примере
p99 не рассчитывается. Алгоритм - линейная интерполяция type-7.
Единичный прогон и синтетический результат не доказывают производительность
реальной системы и не подтверждают SLA.

## Как использовать в другом проекте

Все копии Toolkit - **только для чтения**. По умолчанию отчёт выдаётся в
чате. Для записи пользовательских логов, метрик или отчётов требуется
отдельно согласованное место вне Toolkit. До реального теста подтвердите
владение средой, разрешение, ограничения нагрузки, продолжительность,
возможный ущерб, расходы, данные и критерии немедленной остановки.
Само название `staging` не даёт права запускать нагрузку.

k6, Locust и JMeter можно отдельно оценить для разрешённого проекта,
проверив их актуальные лицензии и возможности по официальным источникам.
Они необязательны и в Toolkit не устанавливаются. Общий GitHub runner
проверяет вычисления и контракты, а не соблюдение реального latency SLO.

**Запрос новичка:** «Проверь, не замедлилось ли моё локальное приложение.
Выбери один безопасный сценарий и честно сравни две версии. Не нагружай
публичные сайты и не записывай результаты в Toolkit».

**Запрос специалиста:** «Определи ограниченную нагрузку constant/step,
зафиксируй входные данные, кэш и прогрев. Подготовь p95/throughput/error
budgets и сравнение baseline/candidate с сырыми наблюдениями. Отклоняй
несопоставимые условия, нарушения функциональности и неразрешённые адреса».
