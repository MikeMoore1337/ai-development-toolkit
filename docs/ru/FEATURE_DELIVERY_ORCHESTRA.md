# Feature Delivery Orchestra - адаптивная оркестрация разработки

[English](../FEATURE_DELIVERY_ORCHESTRA.md) | [Сквозной контракт](END_TO_END_WORKFLOW.md)

Используй **один существующий управляющий процесс**: по умолчанию `feature-delivery` либо `make-feature`, только когда последний явно выбран для проекта. Оркестрация - это **схема распределения ограниченных заданий и передачи результата**, а не новый агентный сервер, фоновый исполнитель, трекер задач или управляющий релизами.

## Когда полезна

| Задача | Режим | Специалисты |
| --- | --- | --- |
| Малое обратимое исправление с понятным поведением | `quick` | Один исполнитель и целевая проверка |
| Новая функция в связанных компонентах | `normal` | Исполнитель; условно исследование и QA |
| Необратимые данные, права, платежи, безопасность, серьёзная неизвестность | `deep` | Проверка допущений, независимый обзор и необходимые разрешения |

Малый diff не отменяет `deep` при существенном риске. Максимум три независимых направления **только когда они реально полезны и доступны**. Наличие навыка не означает запущенного агента. Если клиент не предоставляет субагентов, выполняй проверки последовательно и указывай `SEQUENTIAL`. Поддержку делегации проверяй в текущем Codex/Claude Code/разговорном клиенте; не выдумывай worker-ID.

## Порядок работы

1. **Контракт:** изучи `AGENTS.md` целевого проекта, актуальные Issue/PR, исходные R/AC, ограничения, зависимости, SHA, лимиты и обязательные согласования. Переиспользуй [сквозной контракт](END_TO_END_WORKFLOW.md), без второго источника истины.
2. **Подбор:** выбери `quick`/`normal`/`deep`, ровно один контроллер и до трёх конкретных специализаций. Для каждого задания укажи результат, неизменные критерии приёмки, зависимости, доступные пути и стоп-условия.
3. **Аналитика:** исследование, архитектура, безопасность, UX или QA могут независимо проверять свою часть **на чтение** при настоящей поддержке субагентов. Без неё - последовательная работа без заявления о независимости.
4. **Единственный исполнитель:** менять ветку/worktree должен только один назначенный implementer. Специалисты не редактируют исходники. Конфликтующие миграции, API-контракты, shared components и fixtures выполняются последовательно; чужие ветки не изменять.
5. **Объединение:** сверяй противоречия с принятыми требованиями и наблюдаемым поведением, сохраняй R/AC и ошибочные сценарии, отделяй гипотезы от фактов. После изменения кода повторно запускай целевые тесты и CI на точном новом HEAD.
6. **QA:** при необходимости применяй действующие `qa-strategy` и QA Pack; если в проверяемой ревизии уже имеется `docs/ru/QA_ORCHESTRATION.md`, используй его как дополнительную методику проверки, а не второй контроллер. Самопроверка под другим названием роли - не независимое ревью. `NOT_RUN` не является `PASS`.
7. **Итог:** один отчёт с изменёнными файлами/SHA, R/AC, командами и результатами тестов, окружением, реальными вызовами агентов или `SEQUENTIAL`, разногласиями, ограничениями и следующим действием. `READY_FOR_REVIEW` - ещё не merge, публикация или deployment. Визуальное, правовое и иные необходимые согласования сохраняются.

## Проверяемость

Дополнительная офлайн-проверка: `python scripts/validate_feature_orchestra.py fixtures/feature_orchestra_valid.json`. Пример **синтетический**: `NOT_RUN` и `PLAN_ONLY`. Валидатор отклоняет мнимых субагентов, потерянные критерии, двойное управление, небезопасные пути записи, циклы зависимостей и неподтверждённые зелёные статусы. Он проверяет **согласованность деклараций**, а не подлинность ссылок CI, идентификаторов субагентов и согласований. Не нужны платные API, фоновый сервис, отдельная БД задач и обязательные файлы отчётов.

Для каждого целевого репозитория сохраняй его правила ветвления, QA, визуального согласования и выпуска. Роли разработки не предоставляют права постоянно работающим сервисам. Не обходи явное подтверждение действий, границы приватности и ограничения фоновых заданий.

## Нативная предварительная проверка параллельных worktree (#440)

В существующий `feature-delivery` добавлена **необязательная read-only проверка плана 2-12 независимых задач**. Она не запускает агентов, не создаёт ветки/worktree, не изменяет права, не удаляет файлы и не выполняет merge. Это не второй контроллер, исполнительный процесс или реестр задач; действующая схема `feature_orchestra_valid.json` не меняется.

JSON-план хранится **вне рабочего репозитория** и содержит `schema_version: 1`, `revision` (точный 40-значный SHA), `controller: "feature-delivery"`, `active_controllers: ["feature-delivery"]`, `runtime_state: "CLIENT_RUNTIME_NOT_VERIFIED"` и массив `tasks` из 2-12 элементов. В каждой задаче обязательны уникальный `id`, `base_sha` исходного коммита, `branch`, `worktree`, `writer`, `write_paths`, `shared_contracts`, `depends_on` и `acceptance`. Пути переносимые, без `..`, абсолютных путей, Windows-устройств и wildcard; для области каталога используется завершающий `/`. Путь `worktree` трактуется относительно **родительского каталога явно переданного Git root** и никогда не создаётся валидатором.

```bash
python scripts/validate_feature_orchestra.py --parallel-plan /внешний/plan.json
# По отдельному разрешению: read-only диагностика только явно указанного Git root
python scripts/validate_feature_orchestra.py --parallel-plan /внешний/plan.json --git-root /путь/к/репозиторию
```

Статический режим выявляет пересекающиеся файлы/каталоги, коллизии регистра и Unicode, повторные ветки и рабочие области, повторного владельца независимых задач, пропущенные зависимости и их циклы. При `--git-root` выполняются только читающие Git-команды: `rev-parse`, `status --porcelain`, `show-ref --heads`, `worktree list --porcelain`. Устаревший HEAD, незакоммиченные/неотслеживаемые файлы, занятые ветки и пути, символьные ссылки и junction приводят к отказу. Обнаружение изменённого API/миграции между разными файлами требует явного `shared_contracts` и проверки человеком; статический анализ не доказывает семантическую независимость.

При успехе выводится `STATIC_PLAN_VALIDATED`, **но не разрешение на выполнение**. Остаются `CLIENT_RUNTIME_NOT_VERIFIED`, `NATIVE_SUBAGENTS_NOT_VERIFIED` и `MODEL_EXECUTION_NOT_RUN`. Единственный владелец записи назначается для каждой отдельной рабочей области, но факт захвата владения должен отдельно подтвердить реальный клиент. Для пересекающихся файлов, общего контракта API, миграций и неопределённого владения нужен последовательный порядок.

**Завершение и откат:** сохранить результаты и Git-состояние, проверить незакоммиченные изменения и зависимости, выполнить тесты/CI на точном HEAD, соблюдать штатные разрешения на PR и merge. Нельзя принудительно удалять чужие worktree/ветки, сбрасывать изменения, очищать пользовательские файлы или автоматически захватывать чужую рабочую область. Откат исходников - отдельный проверенный revert PR.

**Сравнение с ECC:** закреплённый исходник `affaan-m/ECC@25278e7d7b6cf6e6a4e7a6c8e10f14ff22f0eb5b` (`scripts/orchestrate-worktrees.js`, `scripts/lib/tmux-worktree-orchestrator.js`). Планирование и обнаружение конфликтов адаптированы как read-only проверки в Toolkit. Автоматическое создание worktree, tmux/dmux, запуск процессов, удаление с `--force` и рекурсивная очистка **не переносятся**. Клиентское исполнение, восстановление реальных сессий, Windows GUI и ускорение моделей - `HOST_EXECUTION_NOT_VERIFIED` / `NOT_MEASURED` до физической проверки.

**Доступ через существующий Toolkit MCP:** тот же проверяющий механизм доступен как read-only инструмент `toolkit_preflight_parallel_plan`. Передай `{"plan": {...}}`, при необходимости добавь `"project": "/абсолютный/путь/к/git-root"` для проверки Git-состояния. Ответ различает `STATIC_PLAN_VALIDATED` и `REJECTED`, содержит коды ошибок и неизменно отмечает `authorization: NOT_GRANTED`, `model_execution: NOT_RUN`. Инструмент не изменяет ветки, не запускает агентов, не создаёт worktree и не разрешает merge. MCP должен быть фактически обновлён и загружен клиентом; изменение GitHub `main` само по себе не обновляет установленный ChatGPT-плагин.

**Дополнительная защита:** запрещены компоненты Git-веток, начинающиеся с точки или заканчивающиеся на `.lock`, и конфликтующие иерархические имена refs. При read-only анализе Git-root не наследуются переменные `GIT_*` процесса и отклоняется символьная ссылка/junction вместо `.git`. Это исключает побочный файл журнала из переменной Git trace.
