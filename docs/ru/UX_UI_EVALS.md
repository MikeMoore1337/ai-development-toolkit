# UX/UI Evals - проверка визуальных доказательств, а не вкуса по чеклисту

[English version](../UX_UI_EVALS.md)

[Issue #192](https://github.com/MikeMoore1337/ai-development-toolkit/issues/192) добавляет **необязательную офлайн-проверку материалов** к существующей [UX/UI Design Orchestra](../../.agents/skills/ux-ui-design-orchestra/SKILL.md). Это не второй оркестратор, генератор дизайна, браузерный рендерер, проверка соответствия WCAG или сервис согласования владельца.

## Набор сценариев

В `fixtures/ux_ui_eval_cases.json` предусмотрены четыре RU/EN задачи: новый сайт, существенный редизайн, ранее согласованная локальная UI-правка и адаптивность/доступность. Для нового дизайна и существенного редизайна обязательны три разных направления. Для локальной правки они не нужны. Фирменные цвета и шрифты **не** считаются автоматически признаком шаблонного SaaS.

```bash
python scripts/ux_ui_evals.py --catalog-only
```

Результат показывает наличие критериев в тестовом наборе, а не качество изображений или реальный рендер.

## Проверка полученного дизайн-пакета

```bash
python scripts/ux_ui_evals.py --packet review.json --asset-root /approved/local/design-preview
```

В `review.json` указываются `schema_version=1`, `scenario_id`, источник дизайн-правил `design_authority`, три направления `directions` с разными сигнатурами композиции и информационной архитектуры (для существенных работ), `chosen_direction`, два `rejected_directions`, три конкретных `template_risks`, `visual_assets`, `manual_reviews`, `owner_approval=PENDING`, `implementation_status=NOT_STARTED`. Это дополнительный формат доказательств: ранее созданный [валидатор UX/UI Orchestra](../../scripts/validate_ux_ui_orchestra.py) остаётся основным структурным валидатором процесса.

Для нового дизайна нужны три визуальных файла с назначением `wireframe:<direction_id>` и одинаковым заявленным размером, а также PNG-снимки победившего направления `winner:desktop` и `winner:mobile`. Скрипт проверяет существование локальных файлов, относительные пути, ограничения размера, SHA-256 и фактические размеры PNG. SVG допускается для эскиза, но **наличие исходника не доказывает просмотр или рендер**. HTML-исходник не засчитывается как готовый снимок финального экрана. Разные контрольные суммы не гарантируют оригинальность композиции.

Ручные критерии: `product-fit`, `task-hierarchy`, `compositional-originality`, `cross-domain-swap`, `mobile-desktop`, `states`, `accessibility`, `motion`, `design-authority`. Для каждого предусмотрены `NOT_REVIEWED`, `ACCEPT` или `REVISE`. Решение требует содержательного объяснения; реальную личность рецензента, работу клавиатуры и взаимодействий, фокус, уменьшение движения и согласие владельца программа самостоятельно не подтверждает.

Результат может быть `VISUAL_PACKAGE_MISSING`, `NEEDS_DESIGN_REVISION` или `AWAITING_HUMAN_VISUAL_REVIEW`. Скрипт **никогда не выдаёт автоматический `OWNER_ACCEPTED`** и не даёт права изменять целевой продукт без отдельного разрешения. Настоящее качество изображения остаётся `NOT_VERIFIED`.

## Процедура реальной проверки

В разрешённом рабочем проекте взять утверждённые дизайн-правила и создать настоящие скриншоты desktop/mobile, проверить состояния загрузки/ошибки/завершения, фокус, скролл и предпочтения reduced-motion. Для серьёзных работ **визуально** сравнить три композиции на одной шкале, зафиксировать причины отказа от двух и провести cross-domain swap test на узнаваемость продукта. Не запрещать фирменную палитру или полезные UI-компоненты. Человек должен увидеть макеты и записать наблюдения отдельно от предположений. Затем требуется явное согласование **конкретной** версии дизайна до изменения интерфейса.

Все фикстуры и unit-тесты синтетические. Продуктовые интерфейсы не менялись, браузерные проверки и платные API не запускались, реальное улучшение UX пока не измерено.

## Дополнительный локальный рендер через Chromium (#486)

Существующий валидатор **не рисует интерфейс**, а проверяет готовые материалы. Новый необязательный помощник `scripts/ux_ui_browser_capture.py` делает PNG-снимки через уже установленный Playwright Chromium, без платных API, автоматического скачивания браузера и отправки данных во внешние сервисы.

Создайте файл `capture-plan.json` **вне Toolkit** (полный пример JSON - в [английской инструкции](../UX_UI_EVALS.md)). В `captures` укажите три разных HTML-эскиза `wireframe:editorial`, `wireframe:catalog`, `wireframe:guide` с одинаковым размером `400x600`, затем один выбранный макет `winner:desktop` (`1440x900`) и `winner:mobile` (`390x844`). Поле `source` - относительный путь к HTML внутри разрешённой папки либо явный адрес локального сервера `http://127.0.0.1:PORT/path`.

```bash
python scripts/ux_ui_browser_capture.py --plan /approved/capture-plan.json --source-root /approved/prototype --output /approved/visual-evidence-v1
```

Папка результатов должна быть новой и находиться **вне репозитория Toolkit**. При наличии установленного системного Chromium его путь можно передать через `--chromium-executable`. Внешние HTTP(S)-запросы и WebSocket блокируются. Если HTML зависит от CDN, шрифтов или внешних изображений, результат может быть неполным; в отчёте будут указаны заблокированные запросы.

Выходные данные: реальные PNG, `capture_report.json` с размерами экранов, SHA-256, горизонтальным переполнением, небольшими целями нажатия и ошибками страницы. Массив `visual_assets` можно перенести в существующий `review.json` для проверки `ux_ui_evals.py`; прочие поля дизайн-пакета и ручная приёмка обязательны. При `NEEDS_LAYOUT_REVIEW` исправьте найденные проблемы и сохраните новую версию скриншотов. `AWAITING_HUMAN_VISUAL_REVIEW` не означает хорошее качество дизайна или одобрение владельца. Программа не оценивает эстетику, WCAG и реальные взаимодействия; проверки в CI синтетические. При отсутствии/блокировке браузера честно сообщайте `PLAYWRIGHT_UNAVAILABLE` / `BROWSER_RENDER_FAILED`, без фиктивных скриншотов.
