# Toolkit Skill Quality v2 — критерии качества навыков (Issue #43)

[English source](../SKILL_QUALITY_V2.md) | [Рубрика качества](QUALITY_RUBRIC.md) | [Языковая политика](LANGUAGE_POLICY.md)

Toolkit Skill Quality v2 — **внутренний стандарт качества**, а не новая версия официальной [спецификации Agent Skills](../AGENT_SKILLS_SPEC.md). Закреплённый официальный валидатор остаётся авторитетным источником проверки формата. Правила предназначены для **новых либо существенно переработанных навыков**. Существующие навыки остаются валидными без добавления одинаковых заголовков. Используйте существующие [офлайновые метрики](../SKILL_QUALITY_METRICS.md), [исключения несовместимых процессов](../QUALITY_RULES.json), [контракты клиентов](CLIENT_COMPATIBILITY.md) и [происхождение](../PROVENANCE_AUDIT.md) вместо создания конкурирующих валидаторов и менеджеров.

## Назначение, активация и границы

Каждый навык должен описывать **определённую повторяющуюся задачу**, положительные условия выбора, отрицательные условия (когда **не** применять), связанные/совместимые навыки и несовместимые управляющие процессы верхнего уровня. Не формулируйте `description` в frontmatter так, будто навык нужен для любого инженерного запроса. Переносимое YAML-описание должно быть кратким и предметным. Условные подробности помещайте в тело и справочники. Качество условий выбора требует смысловой проверки или испытания настоящего агента: сканер ключевых слов не доказывает правильной активации.

Начинайте с [положительного примера SKILL.md](../../templates/skill-quality-v2/example-skill/SKILL.md). При копировании переименуйте и каталог, и YAML `name` в выбранный идентификатор. См. также [пример антипаттерна (EN)](../SKILL_QUALITY_V2_ANTI_PATTERNS.md). Это **авторские образцы**, а не дополнительные навыки из манифеста; автоматически они не устанавливаются.

## Контракт качества и чек-лист ручной проверки

| Область | Что подтвердить при проверке | Требуемое доказательство |
| --- | --- | --- |
| Область применения | Чёткая проблема, границы задачи, положительные и отрицательные условия активации, отличие от соседних навыков | Примеры подходящих и неподходящих запросов |
| Ввод | Цель, контекст, ограничения, существующие артефакты, доступные инструменты/разрешения, недостающие данные и допущения | Один полный и один неполный пример ввода |
| Процесс | Сначала поиск повторного использования, выполнимые шаги, решения, альтернативы, восстановление и критерии остановки | Разобранный пример и реальные команды, где доступны |
| Результат | Конкретный артефакт: код, тесты, диагностика, документ или рекомендация | Наблюдаемый результат и объективный критерий приёмки |
| Безопасность | Инструкции владельца, минимальные права, секреты, недоверенные источники, запрет несогласованных установок/production, разрешение на необратимые изменения | Отрицательный сценарий разрешений и ручной аудит |
| Переносимость | Явно указанные необязательные предположения о клиенте, ОС, платформе, инструментах | Контракт совместимости исходника и реальные испытания, если доступны |
| Контекст | Краткий `SKILL.md`, справочники по мере необходимости, вспомогательные скрипты только при обоснованной пользе | Подтверждение, что детали условные и нет лишнего текста |
| Происхождение | Права на повторное использование и ссылки на внешние источники | Существующий процесс provenance, а не догадка о лицензии |

Агент **не должен повторно спрашивать сведения, уже присутствующие в контексте**. Если информации не хватает, отделяйте безопасные допущения от блокирующих вопросов; не придумывайте полномочия. Не представляйте план как готовое изменение, локальный результат как развёрнутый, а офлайновый тест совместимости как запуск реального клиента.

Новичкам объясняйте последствия решений простым языком и одним понятным следующим действием. Опытным пользователям при необходимости давайте технические альтернативы, компромиссы, команды и граничные случаи. **Условия приёмки и безопасности не зависят от опыта человека**. Не заставляйте пользователя выбирать десятки навыков вручную; применяйте существующие профили и рекомендации без утверждения, что статический подборщик действительно понимает намерение.

Предпочитайте постепенное раскрытие информации: короткий `SKILL.md` и тематические `references/`, детерминированные `scripts/` только при необходимости. Не задавайте произвольный общий лимит размера файла. Убирайте повторения базовых возможностей модели, общих правил безопасности, не относящиеся к задаче советы и функциональность других навыков.

## Таблица положительных и отрицательных условий выбора

Для каждого нового или существенно изменённого навыка подготовьте как минимум **два положительных запроса**, **два близких отрицательных запроса** и по возможности один неоднозначный пограничный случай. По каждому зафиксируйте: ожидаемый навык, обоснование исключения, доступные вводные, фактический клиент/версию при наличии испытания, действительно наблюдаемую активацию и пропущенные/ложные срабатывания. Без реального запуска клиента **observed activation = NOT_MEASURED**, даже если `description` выглядит корректным.

## Уровни доказательств

Это **раздельные последовательные наблюдения**, а не общий балл или гарантии. Указывайте исходный commit, клиент/окружение, если применимо, метод и ограничения. Статусы: `PASS`, `FAIL`, `NOT_MEASURED`, `NOT_APPLICABLE`. Отсутствие теста — **NOT_MEASURED**, а не PASS; для FAIL нужен вывод о причине, для NOT_APPLICABLE — обоснование области неприменимости.

| Уровень | Положительная проверка | Чего она не доказывает |
| --- | --- | --- |
| Source validated | Локальная проверка frontmatter, ссылок, инвентаря и конфликтов; закреплённый официальный `skills-ref` в CI | Упаковку, установку и поведение модели |
| Packaged | Проверенный воспроизводимый архив с манифестом и хешами | Установку |
| Installed | Фактическая установка в определённом версионированном окружении клиента | Обнаружение клиентом |
| Discovered | Настоящий клиент распознаёт зарегистрированный навык; обезличенный лог/UI | Использование навыка |
| Activated | Реальная трасса задачи показывает выбор/чтение/применение навыка | Корректность результата и эффект |
| Effective | Независимый критерий и сравнение «без навыка / с навыком» с регрессиями и опасными действиями | Успех любой будущей задачи |

`skill_quality_metrics.py` выставляет PASS или FAIL для **локальной** проверки исходников, но результат отдельно выполняемого официального `skills-ref` оставляет как NOT_MEASURED **в собственном отчёте**. Packaged, Installed, Discovered, Activated и Effective также остаются NOT_MEASURED. Повторение одинаковых статических измерений это не меняет. Успешная синтетическая установка или контракт совместимости исходника не превращаются в доказательство обнаружения навыка клиентом. Реальные испытания ограничены [политикой Issue #11 (EN)](../SKILL_EVALS.md).

## Необязательная машиночитаемая декларация доказательств

Для существующих навыков декларация не требуется. После согласованных владельцем испытаний можно добавить обезличенную запись в `quality/evidence/` с именем `<skill-id>.json`. [Пример](../SKILL_QUALITY_V2_EXAMPLE.json) явно оставляет все уровни NOT_MEASURED и использует синтетическую ревизию: он **не свидетельствует** о реальном испытании.

Запись содержит `schema_version` (1), `skill_id`, совпадающий с манифестом и названием файла, полный 40-символьный шестнадцатеричный `source_revision` и ровно шесть ключей в `levels`. Для PASS необходимы метод, как минимум один существующий в репозитории артефакт с закреплённым SHA256 и PASS **на всех предыдущих уровнях**. Runtime-PASS дополнительно требует `environment`, `reviewed_by` и `observed_at` в UTC. Для Discovered и выше требуется известный `client_id` из `compatibility/clients.json`. Effective требует объект `comparison` с описанием baseline/candidate. Для FAIL требуется `reason`. NOT_APPLICABLE разрешён только для runtime-уровней и требует обоснования. NOT_MEASURED допускает только `status`.

Существующий `validate_quality.py` проверяет записи и целостность артефактов по правилу **EVIDENCE001**, отклоняет неизвестных клиентов, несовпадения SHA, опасные пути, отсутствие доказательств и фиктивное повышение статуса. Он **не проверяет подлинность логов и независимость рецензента**. Даже текстовый файл с правильным хешем не доказывает реальное испытание. Оценка клиента и модели требует независимой проверки и обезличенных доказательств без токенов, секретов и приватных переписок. Декларации и статические метрики остаются отдельными, чтобы не менять схему метрик и сравнимость базовых снимков.

## Миграция, CI и дальнейшая работа

1. Новые навыки используют шаблон, таблицу положительных/отрицательных случаев, критерий наблюдаемого результата, проверку повторного использования и границы разрешений.
2. Существующий локальный валидатор и закреплённый официальный `skills-ref` проверяют формат; quality gate — ссылки и необязательные декларации; метрики исходников — только статические признаки.
3. Триггеры, пересечение возможностей, риски разрешений и критерии результата **проверяются вручную**, а не по совпадению заголовков.
4. Семантический инвентарь каталога относится к #44, обновление Core/QA — к #45, Frontend/Backend/Fullstack — к #46, версии/документация — к #47, CI — к #48. **Не переписывайте массово** существующие, защищённые QA/Make Feature материалы.

Матрица CI включает Ubuntu Python 3.12/3.13 и Windows Python 3.14, проверки контрольных сумм, происхождения и закреплённый upstream CLI там, где он настроен. Новых зависимостей, реальных вызовов агента или API здесь нет. Без практических испытаний эмпирическое качество, фактическая стоимость токенов и эффективность остаются **NOT_MEASURED**.

## Issue #45: сценарии ручной семантической приёмки

Это **ожидаемое** поведение для будущего испытания клиента, а не подтверждение активации Codex/Claude. Реальное обнаружение, выбор и эффективность агента остаются **NOT_MEASURED**. Связанные статические проверки находятся в `tests/test_skill_quality_v2.py`.

| Навык | Положительные сценарии — ожидаемый выбор | Отрицательные сценарии — не выбирать | Необходимые доказательства |
| --- | --- | --- | --- |
| API Testing | Успешный HTTP + повторное чтение; отрицательный HTTP 404/403; асинхронное событие, только если есть | Стилизация UI; отметка PASS для ненаблюдавшегося события | Отделённые результаты ответов, состояния и возможного события; без скрытых пропусков |
| Test Strategy | Небольшой сервис без полного E2E; границы микросервисов; ограниченный бюджет тестов | Выполнить один известный тест; придумать критические бизнес-потоки без ввода | Выбранные и исключённые уровни тестирования, допущения, непроверенные риски и условия повторной оценки |
| Make Feature | Доступна независимая проверка; делегирование отсутствует; локальные тесты есть, рецензента нет | Самопроверка объявлена независимым PASS; рискованная задача без обязательной проверки; сброс лимита делегаций | Возможности клиента, фактическая идентичность отдельного рецензента при наличии, незакрытые `C*`, бюджеты и остановленные опасные шаги |
| Clear Voice | Редактура пользовательского текста; написание коротких UI-подписей | Исправление Python; проверка SQL; правки структурированного JSON | Режимы редакторской работы не нарушены; ложного технического выбора нет; редактура юридического текста не объявлена юридической экспертизой |

Отсутствие отдельного агента-рецензента может допускать обратимое действие со статусом `DONE_WITHOUT_INDEPENDENT_REVIEW` лишь когда независимая проверка **не обязательна**; иначе статус `INDEPENDENT_REVIEW_PENDING`. Тесты строк кода и документов не являются поведенческими испытаниями ИИ-клиентов. Нельзя объявлять PASS для активации модели на основании синтетических фикстур.
