## Release and technical controls

Run `python scripts/validate_provenance.py --mode inventory --report /path/to/report.json` for inventory consistency (CI). Run `python scripts/validate_provenance.py --mode release` for the mandatory **prepublication gate** on the exact proposed release tree. The second command rejects `owner_gate`/`excluded`, `restricted`, `unknown`, `requires_owner_review`. For this exact owner-identified snapshot it is designed to PASS when all approvals and bytes match; it fails on changed/missing/new scoped files or missing/mismatched owner decisions. This does not itself authorize creating a public release. CI inventory PASS is **not** permission to release.

The release workflow also runs gate checks on tag pushes, post-publication events, and manual archive validation, but **GitHub release:published jobs run after publishing**; they cannot retroactively prevent an owner/API from creating a release. Tag-push checks and the documented mandatory owner approval must occur *before* publication; branch protection/release permission configuration remains a separate owner-admin control. The checksums inventory verifies bytes and completeness, not licensing. Existing released tags and source archives are deliberately unchanged.

The required Linux/Windows PR matrix now runs **both** `--mode inventory` and `--mode release` and uploads machine-readable evidence. An Ubuntu 3.12 CI step also exports the candidate commit using `git archive` into a clean directory, then checks *archive-mode checksums* and the provenance release gate against the exported files; this is a prepublication structural regression, not proof that a future GitHub-generated ZIP was downloaded. Review the published GitHub ZIP separately. A new release-tag push with no provenance validator is explicitly BLOCKED; verification of older releases without one remains `NOT_VERIFIED`. Owner-review classifications (`kind`, `origin`, `license`, `status`, `distribution`) are frozen together with the SHA256 file list: relabeling adapted or redistributed content as `original` or `verified` cannot bypass ID1337. Linked files, malformed JSON types, changed and newly added reviewed files fail the gate. GitHub cannot prevent a privileged user from publishing a release merely by running a post-tag workflow; explicit pre-tag approval remains mandatory. The offline validator checks inventory drift, path containment, allowed statuses/types, source descriptions, claimed SPDX license fields, header conflicts, notices, revisions and false verified declarations. It does not authenticate license signatures, permissions, underlying employment contracts, code similarity, copyright or the identity of rightsholders.

## Onboarding new components

1. Identify the *actual files* to distribute and their author/source and whether code or protected text, not just ideas, was copied.
2. Link the corresponding upstream URL and immutable revision where available. Read license and copyright notices at that revision. For private material, use an opaque non-secret source reference instead of leaking it.
3. Record license using an applicable SPDX identifier or `NOASSERTION` when unresolved. Record required notices and the exact public evidence file.
4. Mark uncertain or restricted materials `owner_gate` or `excluded`. Never infer `verified` from a LICENSE, a public URL or an author's claim.
5. Run offline inventory tests, official skills-ref where relevant, checksums and release preflight. Escalate contradictory rights before publication, without inserting private proof into Git history.
6. Have the owner explicitly approve any permission-based status change or exclusion, and record non-secret references/date. Publishing a previous version is not approval for a future one.

## Issue #195: new external Skill release claims

A new `adapted` or `redistributed` Skill without an existing exact-file owner-approved snapshot is additionally checked in `validate_provenance.py --mode release`: a full upstream commit SHA is required (`EXTERNAL_RELEASE_PIN`) and `NOASSERTION`/`NONE` cannot be treated as a permitted license (`EXTERNAL_RELEASE_LICENSE`). The existing owner-approval and file-hash requirements still apply **even after** these declarations are supplied. Declaring `status=verified` on an external Skill without a full pinned source revision is rejected (`UNPINNED_VERIFIED_EXTERNAL`).

**Backward compatibility is intentional:** previously owner-approved QA and other protected scopes retain their frozen, owner-reported metadata and precise SHA-256 approval records. A historical `NOASSERTION` is **not** upgraded into verified rights or retroactively treated as a new import. This safeguard does not independently authenticate a GitHub commit, confirm license rights or approve publication. Use the optional read-only `external_skill_gate.py --review-context` dossier for a candidate before even proposing a new registry entry; never import unknown code on a clean scanner result.
