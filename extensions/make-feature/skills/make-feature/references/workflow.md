# Приёмы по необходимости

## Понять и диагностировать
C*: источник требования; дано → действие → наблюдаемый итог; среда и проверка. Добавь сохранение, повтор, ошибку и права по задаче. Для дефекта проверь существование/масштаб/корень по реальным данным; один случай не объявляй законом. Для новой функции отдели наблюдение о человеке от гипотезы. Не выдумывай интервью или измерения.

## Исследовать и выбрать
Сначала свой код/настройки/готовые пути. Внешний поиск нужен для неизвестной возможности, актуального API/ограничения или реального выбора; повторное изучение известного stdlib не является этапом по умолчанию. Ищи первичные источники; S*: путь/URL, дата/версия, факт, применимость, проверка. Стабильный подтверждённый факт используй повторно; изменившийся проверь.

Серьёзные кандидаты: исправление процесса, настройка готового, интеграция, расширение своего, новая разработка. Выбери наименьшую достаточную сложность по C*, пользе, времени/цене, риску и стоимости выхода. ROI только при обоснованных числах и единицах; измеренное/прогноз/unknown отдельно. До/после объясняет, что реально изменится. При одной очевидной реализации не создавай исследование и фиктивные альтернативы.

Главный премортем: почему результатом не пользуются или он ломается в реальном сценарии? Существенный риск → сигнал/ограничение/проверка. Масштаб и нагрузку сравни в нескольких сценариях только если они влияют на выбор.

## Проверить выбор в deep
Один пакет: цель/C*/факты → D*/контракт → T*/приёмка. Критик обосновывает ошибку, несовместимость или риск через место/последствие/проверку. Свежий судья разделяет реальную ошибку, обоснованный риск, предпочтение и опровержение. Пересобери по подтверждённому; причины отклонения сохраняй. Не требуй заданного числа замечаний. Повторное оспаривание нужно при новом существенном выборе, не по смене заголовка документа.

## Испытать и спроектировать
Проверь допущение, которое способно разрушить решение, до большой реализации: настоящий вход, observable success, разрешённая среда, предел и очистка проб. Нет такого риска — отдельная проба не нужна. Мок проверяет внутренний контракт; недоступная реальная интеграция остаётся unverified.

Контракт: часть → источник истины → путь доступа → владелец записи; интерфейс, единицы/null, ошибки, повтор, права, сохранение/миграция/откат по применимости. Сверь совместимость пунктов, наличие механизма и актуальность опорных значений. T*: нужный C*, входы, зависимость, точные файлы, результат и проверка. Не включай задачу, не ведущую к критерию.

## Реализовать и принять
Один поведенческий тест нового изменения реально падает до кода по нужной причине; затем минимальная реализация и соответствующая регрессия. Для текста или уже проверенного механизма не выдумывай TDD-церемонию. Baseline-падения и чужие правки отдели от новых.

Приёмка одним независимым проходом: требования, реальное использование, качество и безопасность по риску; плюс понятность передачи. Для существенного риска приёмщик может поручить узкий отдельный аудит только в общем бюджете. Для замечания — причина/место/C*/воспроизведение. После исправления повтори затронутый случай и основной путь, сохрани новую версию доказательства. Следующая одинаковая попытка без новой гипотезы не запускается.

## Интерфейс и интеграции
Если задача включает UI: вход/действие/ожидание/успех/пусто/ошибка; стиль и компоненты проекта; реальные браузер, ширины, клавиатура и console/network по применимости. Сохранённый скриншот должен быть просмотрен; макет не является готовой функцией. Для CLI/бота нужен рабочий сценарий команды/диалога, не веб-экран.

Интеграция: настоящий вход → заявленная поверхность → сохранение → read-back из источника истины. `200`, green build и отчёт автора сами результат не закрывают. Проверяй швы/повтор/нештатный исход по C*. Сравни до/после одним способом; польза и токены остаются неизвестными без измерения.
