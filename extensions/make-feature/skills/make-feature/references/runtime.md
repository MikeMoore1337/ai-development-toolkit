# Исполнение и предел

## Инструменты
Сверь фактические files/terminal/delegation/schema, поиск и UI по задаче. Не загружай справочник всех возможностей. Существующие подтверждённые инструменты повторно не «доказывай» отдельным агентом. Для настоящей независимости нужен отдельный контекст, не смена роли в чате. Оставь доступный контекст для приёмки; не исчерпывай лимит среды исполнителями. Уже существующий отдельный агент подходит, если он не участвовал в реализации проверяемой версии; его прежнюю роль и реальный ID фиксируй. Если он недоступен — разрешённую работу продолжай, независимую приёмку оставь открытой.

Hermes может иметь leaf или background workers: [официальная делегация](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation/). Порядок ID/возврата сверяется по установленной версии; выдуманных API нет.

## Общий бюджет
Сначала workspace init, затем один общий бюджет. Из каталога навыка:
```text
python3 scripts/budget.py --project PROJECT --slug SLUG init --mode quick
python3 scripts/budget.py --project PROJECT --slug SLUG status
python3 scripts/budget.py --project PROJECT --slug SLUG reserve --kind delegation --key review-1
```
Init допускает --delegations/--repairs/--minutes для меньшего пользовательского предела или явно выбранного общего задания. Счётчики init повторно не сбрасывает. Каждая попытка dispatch, включая неудавшуюся, резервируется до вызова; повтор использует новый ключ после сверки предыдущего исхода. Исправление после отказа приёмки отдельно reserve --kind repair. Обычная разработка и baseline-failure не являются такими исправлениями. Повторная независимая приёмка тоже расходует delegation.

Если reserve отклонён, новые задания не запускай; сохрани фактическое продолжение. Оставь время на возврат/приёмку и текущий checkpoint. Внешний deadline задания не позже остатка запуска. Helper не перехватывает вызовы LLM и не останавливает уже работающие процессы: гарантия счётчика действует только для прошедших reserve запусков. Не обходи его новым slug/DB. Изменение глубины не пополняет бюджет; новый риск фиксируется, уже потраченное сохраняется.

Токены/деньги записывай по реальному provider/session usage всех контекстов, с источником и полнотой. Если данных нет — unknown, не ноль и не оценка по размеру Markdown. При жёстком токен-лимите без доступного контроля не обещай его соблюдение. Бюджет helper считает делегации/исправления/elapsed; запись usage сама остаётся отдельным receipt.

## Журнал исполнения по необходимости
Quick и одна normal-задача могут жить в четырёх Markdown плюс бюджет/receipts. State.py нужен для зависимых фаз, нескольких исполнителей, прерванного execution или формального evidence manifest; один пишущий worker. Точный интерфейс — [state-cli](state-cli.md); --full читает полные receipts, обычный ответ краткий. SQLite не изолирует посторонних редакторов.

При использовании state: claim.owner — ключ задания до dispatch; реальный ID после запуска/синхронного возврата связывается bind. Родитель check после bind/остановки worker; независимый reviewer не принадлежит implementers. Check — короткая прочитанная команда с --allow-execute; timeout не гарантирует остановку потомков.

## Возобновление
Индекс → принятое решение/контракт → незавершённая задача → бюджет status. Проверь прошлые процессы и эффекты; неизвестный исход не повторяй. В ledger recover сохраняет interrupted/блокировку; при обрыве до bind восстанови прежний ID до reconcile. Только после остановки, read-back и сверки эффектов назначай новое исполнение. Смена решения инвалидирует затронутое, не всю историю. Сохранённый контекст не является долговечным runner.
