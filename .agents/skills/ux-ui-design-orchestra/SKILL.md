# UX/UI Design Orchestra

A **task-scoped coordinator**, not a resident agent, second release controller, tool installer, or permission to rewrite the UI. The target is the **user's project**. Toolkit remains read-only when borrowed by another project. No report, asset, temporary file, prompt trace, or screenshot of a third-party project belongs in Toolkit.

**Mandatory design triggers:** natural requests such as "make a beautiful website", "design a fitness club landing page", "нарисуй лендинг", "улучши интерфейс", "audit my UI", "оркестрация UX/UI", "устранить нейрослоп". **This is the primary coordinator, not an optional method.** The user need not know skill names or provide a specialist prompt; `ux-design-process`, `frontend`, `feature-delivery`, and `component-architecture` are supporting roles, not substitute routes.

**Negative triggers:** backend-only code, copyediting alone, already approved minor code fixes with no design decision, a request to install every skill, or a request to change styles without examining the local design contract.

**Mode is inferred from intent and project evidence:** `create-design` for a new screen/site without a relevant existing UI; `audit-proposal` for improving an existing UI (the existing-UI default); `audit-only` for diagnosis only; `implement-approved` only after evidenced visual acceptance. Creation and audit are **read-only with respect to the target application**: discovery -> specialist work -> one coherent concept -> actual visual package when tools allow -> owner gate -> proposed implementation plan. See [new design workflow](references/CREATE_DESIGN.md) for nontechnical users. Do not edit application, design tokens, CSS, tests, `DESIGN.md`, assets, or configuration in the target project in this mode. Do not create issue/PR/branch in the target solely to record an audit; respond in chat by default. Work explicitly authorized to develop this Toolkit skill is a separate task.

Read [workflow](references/WORKFLOW.md) and [handoff contract](references/HANDOFF.md) before coordinating. For new designs read [create-design](references/CREATE_DESIGN.md). Use [specialist routing](references/SPECIALISTS.md) to choose specialists; **do not run all installed skills**. Find and obey the target's `AGENTS.md`, source-of-truth design contract, actual UI and owner approval/release rules. The local design contract overrides general fonts, palette, glass, glow, motion, and "AI slop" prohibitions in upstream skills.

## Tool-native creative freedom and visual continuity

The Orchestra **coordinates** skills; it does not dictate art direction, forbid aesthetics or replace the original design methods. No categorical ban on hero sections, product cards, grids, gradients, glass, dark/light palettes, typography, photography, dashboard patterns, animations or familiar e-commerce/SaaS layouts. Select those choices from the real task, user's taste, project design system and the **unmodified, available upstream skills**. Do not add a fake "originality" rule that rejects a design merely because it uses a common pattern. A critique can raise a context-grounded concern, not impose a universal style prohibition.

**No arbitrary creative quotas.** Do not require exactly three alternatives, three wireframes, three template risks or a mandatory cross-domain swap test. Follow an original skill's actual exploration procedure when invoked and the user's requested number of options; otherwise use as many (including one) as useful. If alternatives are shown, actually view and compare the rendered alternatives. Do not claim sources, agents, screenshots or comparisons that did not run.

**Retain strong work.** When a user has preferred/approved an earlier concept, keep immutable references to its images, version and strengths **in the task context or target project, never in Toolkit**. Inspect that version alongside each significant proposed replacement at comparable viewports. Compare composition, typography, imagery, visual expression and usability with observations and uncertainty, and present KEEP/REFINE/PROPOSE with the owner's preference taking priority. Rework the preferred version instead of replacing it by default. Do not silently downgrade its visual identity because a new candidate passes technical tests.

**Separate evidence channels.** Browser screenshots, responsive/overflow/keyboard and code QA provide technical evidence. The aesthetic review is a human/expert judgment that cannot be certified by a checksum, a CI PASS, a script or an "anti-template" checklist. Before requesting approval, supply real accessible visuals when available and mark missing visual proof honestly. A new design or substantial visual change requires explicit owner visual agreement before modifying the target application. Existing release/security/privacy/tool-execution gates remain unchanged.

## Execution

1. **Route and brief:** choose `create-design`, `audit-proposal`, `audit-only` or `implement-approved` using [workflow](references/WORKFLOW.md). Inspect the target project's brand, design source and owner instructions when accessible. Do not invent brand facts, installed tooling or prior approvals.
2. **Follow upstream methods:** read and execute genuinely available original skills through authorized client tools, without modifying their prescriptions. Select complementary specialist perspectives from [specialists](references/SPECIALISTS.md); in `ALL_THREE` mode actually invoke all three or disclose the blocker (#449). A URL is only `REFERENCE_ONLY`.
3. **Explore without quotas:** use the task-appropriate number of concepts and present genuine visual variants when helpful/requested. Record inputs, references, and the method actually used. No random template policing or compulsory redesign for being familiar.
4. **Compare and retain:** when a previous user-preferred or accepted reference exists, preserve its version/refs and strengths, compare the candidate side-by-side, and keep/rework the stronger version by default. If the outcome is uncertain, show the trade-off and ask the owner rather than asserting a new "best" design.
5. **Verify independently:** run supported viewport, accessibility and interaction checks for the artifact; keep observed technical checks separate from visual taste. Real subagents are at most three simultaneous read-only workstreams and must have verifiable IDs; use `SEQUENTIAL` if none are supported.
6. **Visual handoff:** report final concept(s) with actual preview references and an honest outcome `AWAITING_VISUAL_APPROVAL` only when a visual package is available. A single mobile-only screen may need only a mobile preview. Rendered HTML is not necessarily an interaction-tested site. Missing preview means `VISUAL_PACKAGE_MISSING`.
7. **Approval and implementation:** only after explicit owner approval of a specified design version may the separate `implement-approved` workflow modify the target application. CI/merge/deploy require their separate permissions.

## Evidence and truth

Use [handoff](references/HANDOFF.md). Optional structured audits can be checked **without modifying anything** using `python scripts/validate_ux_ui_orchestra.py <report.json>` from a Toolkit development checkout; it validates a **declaration**, not real agent provenance or visual quality. Do not require a JSON file from a beginner. The signed-off artifact is the coherent design package, not the validators' PASS.

The optional structural checker confirms only declarations and reference consistency; it **cannot** inspect pixels, independently establish visual originality or prove the files really exist. If an agent claims to have compared visual alternatives, it must actually view the relevant generated artifacts; no fixed number of sketches is required.

Skill availability is three states: `LOADED` (source actually read), `REFERENCE_ONLY` (URL/method consulted), `UNAVAILABLE`. Worker execution is `ACTUAL_SUBAGENT`, `GENERIC_SUBAGENT`, or `SEQUENTIAL`, with identifiers only when verifiable. Browser proof is `RENDERED`, `SOURCE_ONLY`, or `NOT_OBSERVED`. If client capabilities, branch, external skill or evidence are missing, never invent them.

No paid API, background service, private data export, unauthorized screenshots, global plugin installation, new controller, merge or deployment is required or permitted by this skill.

## Original three-skill mode - opt-in (#449)

The existing coordinator additionally supports the user-selected `original_design_skills.mode=ALL_THREE`. **Do not create another controller.** When this mode is selected and the original packages are installed/trusted in the active client, use all three *unchanged originals* for the same project-verified brief: `ui-ux-pro-max` for design-system/stack research, `design-taste-frontend` for distinctive concepts/compositions and `impeccable` for shaping, critique and polish. Respect the actual project brand and limitations. Run real subagents only where available; sequential execution is valid. Do not let concurrent workers edit the same UI. Standard mode retains selective specialist routing.

A GitHub reference is `REFERENCE_ONLY`, a native skill directory is `FILES_PRESENT_UNATTESTED`, a skill read in context is `LOADED` and a documented *actual client invocation* is `INVOKED`. They are different claims. In all-three mode, first install any missing required original through the host after checking its source, license, pinned revision and files, within granted permissions; prefer user scope and preserve existing files. Verify the installation and run the original before continuing; reference-only instructions do not satisfy a required original. If setup is blocked or invocation remains unverified, return the blocked status and do **not** claim `AWAITING_VISUAL_APPROVAL`. Never fabricate worker IDs. The optional `original_design_skills` ledger in the existing report is checked by `scripts/validate_ux_ui_orchestra.py`, whose structural PASS is not independent runtime evidence. Local read-only discovery: `python scripts/validate_ux_ui_orchestra.py --inspect-originals TARGET`; also inspect the active client's user and ancestor skill directories. A trusted installed specialist's permitted local context launcher may run when needed; do not execute unverified downloads, hooks or paid APIs. See `docs/UX_UI_DESIGN.md` for original distribution and setup rules.

**Local preference binding:** read the existing validated Toolkit preference preview (`scripts/toolkit_preferences.py --target TARGET`) when that client and filesystem are available. The effective `skills.design_originals=ALL_THREE` is a task-routing preference, not installation or execution permission; no model/binary/installer may start solely because the preference is enabled. `STANDARD` keeps the current select-as-needed route. When the preview is unavailable, do not assert that the user-local setting was loaded.
