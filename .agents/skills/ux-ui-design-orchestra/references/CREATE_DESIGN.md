# Create-design - tool-native visual exploration

Use `create-design` for a new site/screen without an applicable approved reference. The existing UX/UI Orchestra is a task-scoped coordinator, **not a renderer, new design model, or replacement for original specialist skills**. It must be loaded by the active client to influence work.

## Tool-native creative freedom

1. Infer an ordinary-language brief: product, audience, primary action, required content, unverified facts, constraints and relevant device sizes. Ask only consequential questions. If there is an existing design system, respect it; if not, propose context-appropriate defaults.
2. Use the requested, genuinely loaded original design tools in their **own intended workflow**: Impeccable, Taste Skill, UI UX Pro Max or others when available and authorized. Never present a cited URL as an invoked skill. An observed standing or private-plugin `ALL_THREE` choice already opts in; the user need not repeat it. Load each selected original before rendering, then execute its applicable process or report the concrete blocker (#449). A native scope exclusion is `NOT_APPLICABLE_NATIVE_SCOPE` with the source and reason, not an invocation or a successful all-three result. For a static mockup, execute applicable research and concept steps without inventing HTML/browser verification. Do not silently replace original methods with Toolkit stylistic rules.
3. **No mandatory UI/UX prohibitions or quantities.** Hero photography, product grids, cards, gradients, dark colours, serif typography, familiar e-commerce patterns, unconventional structures and motion are all possible options. One concept, three concepts or another number may be appropriate. Follow the user's brief and tool-native design workflow rather than imposing three sketches, a cross-domain swap test or "generic template risk" quotas.
4. If exploring alternatives, create actual comparable low-fidelity visual artifacts (SVG, PNG, HTML or an authorized browser capture), view them and explain strengths/trade-offs. A text-only list is `TEXT_SPEC`; do not describe an unrendered variant as `RENDERED`. Do not manufacture extra weak options only to satisfy a count.
5. When the user has preferred or approved **any previous visual**, preserve that candidate's visual identity and available image links as a source of truth in the consumer project's working context. Compare every significant revision against the baseline at comparable size/state: layout, typography, subject photography, visual expression, task usability. If the new candidate is weaker or the trade-off is uncertain, prefer keeping/refining the baseline over gratuitous replacement.
6. Separate results from judgments. Technical browser/QA checks (layout, accessibility smoke, interaction, viewport fidelity, runtime errors) do not measure aesthetic excellence. Do not describe an automatic checker as having chosen the more beautiful direction; a reviewer or the user must judge actual images.
7. Show the relevant rendered previews for user approval. A mobile-only design needs no forced desktop mockup; a responsive store usually benefits from both. Present whether the recommendation is `KEEP_BASELINE`, `REFINE_BASELINE`, `PROPOSE_CANDIDATE` or `UNDECIDED`. When no visual renderer exists, report `VISUAL_PACKAGE_MISSING` and provide the useful design brief without claiming approval readiness.
8. Stop before modifying the target application. Only an explicit owner approval of a specific visual revision permits a separate `implement-approved` task. Installation of tools, paid services, security-sensitive actions, releases and deployment retain their distinct authorization gates.

## Source, media and review integrity

Do not fabricate prices, reviews, conversion metrics, delivery terms, source rights, screenshots, skill invocations or user research. Treat images generated solely for concept previews as illustrative, not licensed retail photography. Keep all private design assets, preview files, notes and evidence in the target project or chat, never in Toolkit.

A good visual comparison explicitly separates `observed`, `inferred` and `unknown`. A user's stated preference outranks a generic "creative direction" rubric. A reviewer can critique a particular layout, but a stylistic convention alone is never an automatic error. For genuinely new work without an approved/preferred reference, do not require a fictional predecessor.

## Minimal example

**User:** "Нарисуй лендинг магазина манго."

**Behavior:** identify buying goals and unknown business facts; use actual available design methods to sketch one or more promising directions, show real previews on relevant viewports, and request a visual decision. A large hero photo, a product catalog or a simple editorial shop are all valid design choices. If the user preferred an earlier expressive MangoLand-like mock, preserve and improve it instead of replacing it with a plainer "technically green" design. These are illustrative product concepts, **not reusable templates or stylistic bans**.

## Honest evidence

- `RENDERED`: actual created and referenced visual file/browser output
- `SOURCE_ONLY`: source inspected, no rendered result
- `TEXT_SPEC`: textual proposal, not a picture
- `VISUAL_PACKAGE_MISSING`: requested images could not be generated
- `AWAITING_VISUAL_APPROVAL`: the user can inspect actual relevant images, but has not approved the selected revision
- `OWNER_ACCEPTED`: only after an explicit owner decision on a specific version
- `INTERACTIVE_VERIFIED`: only after actually exercising working controls

A structural report can check consistency, **not aesthetic quality, actual ownership of screenshots, or installation and invocation of external skills**.
